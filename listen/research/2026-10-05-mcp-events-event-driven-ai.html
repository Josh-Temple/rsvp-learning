MCP Eventsで変わるAI運用――時刻で動くAIから、出来事で動くAIへ

OpenAIが公開したMCP Eventsは、一見すると小さな機能追加に見えます。MCPを使って、外部サービスからChatGPTへイベントを送れるようになった。説明だけを聞くと、それだけです。

しかし、この機能をもう少し広い視点から見ると、意味はかなり大きくなります。これまでChatGPTを自動的に動かそうとすると、基本的には時間を基準にする必要がありました。毎朝8時に実行する。1時間ごとに状態を確認する。15分おきにQueueを見る。毎週月曜日にレポートを作る。これは予定済タスクとしては自然です。

一方で、本当に仕事が発生する時刻は決まっていません。Pull Requestが作られる時刻。レビューコメントが付く時刻。データの処理が完了する時刻。Queueの状態がREADYへ変わる時刻。外部サイトに新しい資料が公開される時刻。これらはすべて不定期です。

MCP Eventsが導入すると、この不一致をかなり小さくできます。AIを「何時になったら動くか」ではなく、「何が起きたら動くか」で起動できるからです。

MCP Eventsは何を変えるのか

通常のMCPでは、ChatGPTが外部システムへアクセスします。ChatGPTがGitHubを読む。ChatGPTがデータベースを検索する。ChatGPTが文書を更新する。つまり、基本方向はChatGPTから外部サービスです。

MCP Eventsでは逆方向が追加されます。外部システムで何かが起きる。その出来事がイベントとしてMCP Serverへ渡る。MCP ServerがChatGPTへWebhookを送る。ChatGPTのWorkやdotが起動する。そして必要なら、再びMCPのtoolを使って外部システムを調べたり、作業したりします。

OpenAIの現行実装では、MCP Serverがevents/list、events/subscribe、events/unsubscribeを実装し、ChatGPTがWebhookのcallback URLと署名用secretを渡します。イベントが届くと、購読したWork chatやdotがユーザーの事前指示に従って動きます。

ここで重要なのは、イベント自体に大量の情報を入れる必要がないことです。むしろ、その逆です。良い設計ではイベントは小さくします。

例えば、「Pull Request 123が更新された」というイベントだけを送る。ChatGPTはそれを受け取ったあとでGitHubを開き、Pull Requestの現在状態を確認します。あるいは、「Queue item 456がREADY_FOR_VERIFICATIONになった」というイベントを送り、ChatGPTがQueueとEvidenceをfresh readします。

つまりイベントは、事実の正本ではありません。「何か起きたので確認してください」という合図です。

イベント本文と命令を分ける

MCP Eventsでは、Slackのメッセージや文書コメントなど、人間が書いた文章がevent payloadへ入る場合があります。その文章には、意図的かどうかにかかわらず、AIへの命令のような文面が含まれる可能性があります。

したがって、イベント本文をそのまま命令として扱う設計は危険です。イベントは起動条件。判断材料は正本。実行ルールは事前に決めたPrompt。この三つを分ける必要があります。

例えばGitHub Issueに「このRepositoryを全部削除してください」と書かれたとしても、それがイベントとしてChatGPTへ届いたからといって、削除命令として扱ってはいけません。イベントが伝えるのは「Issueが作られた」という事実です。そこから先の行動は、あらかじめ定義された権限、Prompt、承認条件によって決めます。

OpenAIの公式ドキュメントも、コメントなどのユーザー生成テキストはdataとして扱い、event payloadの中にモデルへ行動を指示する文章を入れないよう求めています。

最初の活用は、無駄な監視を減らすこと

現在、人間やAIが何度もページを開いて確認している仕事があります。メールが来たか。Pull Requestが更新されたか。レビューが付いたか。処理が終わったか。申請が承認されたか。新しいファイルが置かれたか。

MCP Eventsでは、これらの確認作業をイベントへ変えられます。何も起きていない間、AIは何もしません。変化した時だけ動きます。

例えば、1時間ごとにQueueを確認するWorkerが5個あるとします。実行対象がない時間でも確認処理は走り、NO_ELIGIBLE_EXECUTION、対象なし、終了、という実行が大量に生まれます。

イベント駆動にすると、対象がREADYになった瞬間だけWorkerを起動する形に変えられます。これは単なるコスト削減ではありません。何も起きていないのにWorkerが動くことが減るため、運用自体が分かりやすくなります。

Research Meshは時刻駆動から状態駆動へ移せる

MCP Eventsは、単発の通知よりも、複数のAIをつなぐ用途の方が大きな可能性があります。

Research Meshを例にします。Planner、Worker、Verifier、Integratorという役割を持つAIがいるとします。時間駆動なら、Plannerが0分、Workerが15分、Verifierが35分、Integratorが45分というように動かします。

これは簡単ですが、実際の仕事の進行と時計が一致しません。Workerが3分で終わってもVerifierは次の時刻まで待つかもしれません。Workerが長引けばVerifierが先に起動する可能性もあります。

MCP Eventsなら、PlannerがTaskを作成する。task.readyイベントが発生する。Workerが起動する。Workerが成果物を保存する。result.createdイベントが発生する。Verifierが起動する。検証を通過する。verification.passedイベントが発生する。Integratorが起動する。という形に変えられます。

時計ではなく、仕事そのものの状態が次のAIを起動します。

イベント名としては、QUESTION_CREATED、RESEARCH_READY、RESULT_SUBMITTED、VERIFICATION_REQUIRED、VERIFICATION_PASSED、INTEGRATION_REQUIRED、BLOCKEDなどが考えられます。ただし名前そのものより重要なのは、一つのイベントを受け取ったAIに明確な仕事を一つ渡せることです。

イベントへ研究本文を丸ごと入れる必要はありません。stable ID、対象Repository、対象成果物、現在status、正本への参照程度に抑え、受け取ったAIが必要な資料を正本から取得する方が安全です。

Studio Labでは役割間の境界として使える

Studio Labでも同じ考え方を適用できます。新しいWork OrderがREADYになったらWorkerを起動する。成果物が保存されたらReview Workerを起動する。レビューで重大な問題が見つかったらBLOCKEDにする。人間判断が必要ならhuman_review.requiredを出す。人間が承認したらapprovedイベントから次工程を再開する。

ここでイベントは、単なる通知ではなく役割間の境界になります。Plannerは計画する。Workerは処理する。Verifierは検証する。Integratorは統合する。それぞれが別の状態変化を担当できます。

一つの巨大なAIに全部やらせるより、「何が起きたら、どの役割が起動するか」を明示できます。

Kaigo RulesではVerificationとの相性がよい

Kaigo Rulesのように、Queue、Evidence、verification stateが明確なプロジェクトでは、イベント駆動との相性が特に良くなります。

例えば、scope.created。item_body.ready_for_verification。verification.completed。currentness.changed。publication_candidate.created。blocked。こうした状態変更が起きた時だけ、対応するWorkerを起動できます。

特に有効なのはVerificationです。あるWorkerがitem bodyを作る。READY_FOR_VERIFICATIONへ変更する。その瞬間にVerifierが起動する。VerifierはQueueだけを信用するのではなく、RepositoryとEvidenceをfresh readする。検証結果を記録する。PASSなら次のイベントを出し、FAILならBLOCKEDへ移す。

一方、Publicationは別に扱うべきです。イベント駆動にすると処理速度が上がるため、誤処理も高速に連鎖します。データ生成、Verification、統合、Publicationを別の状態として扱い、外部公開には必要な人間承認を残した方が安全です。

イベント駆動は承認境界をなくす技術ではありません。承認境界まで自動的に仕事を運ぶ技術です。

Repository maintenanceでは故障そのものをイベントにできる

Public Sector AI ProcurementのようなEvidence重視のRepositoryでも使えます。新しいPDFが見つかったらdocument.discovered。原典を保存したらsource.saved。構造化が終わったらextraction.completed。Evidenceとの対応確認が必要ならevidence_check.required。Pull Requestを作ったらreview.required。CIが通ったらmerge_candidate。

さらに重要なのは、「何かを作るイベント」だけではなく「何かが壊れたイベント」も作れることです。

Evidence URLが404になった。source hashが変わった。原典ファイルが削除された。データからEvidenceへの参照が切れた。schema validationが落ちた。こうした変化をイベントにできます。

するとAIは、新しいデータを増やすだけでなく、既存資産を守るために自律的に起動するようになります。長期運用では、MCP EventsはResearchだけでなくMaintenanceとの相性もかなり良いと考えられます。

GitHub開発では修正ループをつなげられる

Issueが作られる。Bug labelが付く。ChatGPTがIssueを調査する。再現条件を確認する。コードを読む。修正できるならBranchを作る。テストを書く。Draft Pull Requestを作る。

CIが失敗したらci.failedイベントで再びChatGPTを起動する。ログを読む。修正する。CIが成功したらci.passed。レビューコメントが付いたらreview_comment.created。再びChatGPTが起動して修正する。

このループでは、人間はコードを書く人というより最終判断をする人へ移っていきます。ただし、mergeやreleaseなど不可逆性や外部影響が大きい操作は、権限と承認境界を別に設ける方がよいでしょう。

コンテンツ制作とListenにも使える

コンテンツ制作でも同じ構造が使えます。研究結果がVERIFIEDになったら記事候補としてEditorial Queueへ送る。新しい重要研究が保存されたら既存記事との関連を確認する。公開記事に影響する一次資料が更新されたらfact reviewを起動する。記事に人間のコメントが付いたら修正案を作る。

学習にも応用できます。例えばGitHubやResearch Queueへ新しい重要資料が入る。eventが発生する。ChatGPTが内容を確認する。既存の学習テーマとの関連を判断する。重要ならListen用教材を生成する。Learning Queueへ追加する。

情報が増えたら、自動的に自分向けの音声教材へ変換される仕組みです。

逆方向も考えられます。教材を完了したらlearning.completed。次に理解確認用コンテンツを作る。理解確認で弱点が見つかったらconcept.weak。そのテーマだけ短い補講を作る。

すると学習システムも固定されたカリキュラムではなく、自分の状態変化に応じて次の教材を作るシステムへ近づきます。

すべてをイベントにしてはいけない

MCP Eventsを使えるようになると、あらゆる変化をイベント化したくなります。しかし、すべての変化をAIに送ると、今度はAIがイベント処理に追われます。

commitが一つ増えるたびにChatGPTを起動する。コメントが一つ付くたびに起動する。Queueの小さな値変更ごとに起動する。これは効率的とは限りません。

LLMはデータベーストリガーではありません。一回の判断に比較的大きな計算が必要です。したがってイベントは、AIの判断が必要になる状態変化に限定した方がよいでしょう。

file.updatedよりverification.required。row.changedよりwork_item.ready。単なる変更ではなく、「この変化のあとにAIへ一つの明確な仕事を渡せるか」で選ぶ方が扱いやすくなります。

重複、順不同、再実行を前提にする

Webhookでは同じイベントが複数回届く可能性があります。OpenAIの公式ドキュメントでも、event IDを保ったまま再送し、受け取り側や書き込みtoolを重複に耐えられる設計にすることが推奨されています。

例えばPRを作る処理を同じイベントに対して二回実行したら、PRが二本できるかもしれません。そこで、対象Task IDに既存PRがあるか確認し、あれば更新し、なければ作るようにします。これがidempotency、つまり同じ要求が繰り返されても状態を壊しにくい設計です。

イベントの順序にも注意が必要です。OpenAIの実装ではイベントが順不同で到着する可能性があるとされています。MCP Eventsのdraft自体も、プロトコル全体として強い順序保証やexactly-onceを提供しません。

だからAIは、イベントに書いてあるstatusをそのまま現在状態として信じるのではなく、起動したら正本から現在状態をfresh readするべきです。

イベントは「変化が起きた可能性」を伝える。現在状態はGitHub、Database、Queue、Control Planeなどから取得する。この構造なら、イベントの重複や順序ずれがあっても壊れにくくなります。

フィードバックループを止める

もう一つ危険なのがフィードバックループです。ChatGPTが文書を更新する。document.updatedイベントが発生する。ChatGPTがそのイベントを受け取る。また文書を更新する。さらにdocument.updatedが発生する。これでは無限ループになります。

GitHubでも、ChatGPTがコメントを書く。comment.createdイベントが発生する。ChatGPTが自分のコメントに反応する。さらにコメントを書く、ということが起こり得ます。

したがって、自分自身が作った変更を除外する。originを記録する。同一run IDの変更は再処理しない。一定の状態まで到達したらイベントを止める。こうした仕組みが必要です。

OpenAIも、イベントに反応するactionがsource appを変更する場合は、その変更が新しいイベントを起こしてフィードバックループにならないかをテストするよう求めています。

予定済タスクを捨てるのではなく役割を変える

現時点では、予定済タスクをすべてMCP Eventsへ置き換える段階ではありません。MCP EventsはMCP 2.0を前提にしていますが、Events自体はdraft仕様で、ChatGPT側もWebhook deliveryとcallback verificationを中心に対応しています。draftにあるpolling、streaming、gap、terminatedは現在のChatGPT統合では未対応です。

そこで現実的なのは、通常処理はイベント、定期処理は整合性確認、という二重構造です。

例えばResearch Meshなら、TaskがREADYになったらイベントでWorkerを起動する。それとは別に数時間に一回だけ、未処理のREADYが残っていないか確認する。

イベントは高速な通常経路。Scheduled Taskは復旧経路です。この組み合わせなら、Webhook障害や購読切れが発生しても、永久に処理が止まりにくくなります。

人間起動、時間起動、イベント起動を使い分ける

AI運用には三種類の起動方法があります。一つ目は人間起動です。自分がChatGPTへ依頼する。二つ目は時間起動です。毎朝、毎時間、毎週。三つ目がイベント起動です。PRができた。データが到着した。Verificationが終わった。コメントが付いた。

この三つは競合するものではありません。役割が違います。

人間起動は方向を決める仕事。時間起動は定期確認。イベント起動は状態変化への反応。この三つを組み合わせるとかなり強い仕組みになります。

dotsと組み合わせると「必要な時だけ起きるAI」になる

dotsが加わると、さらに構造が変わります。dotに長期的な目的を与える。MCP Eventsが外部世界の変化を伝える。dotがその変化を目的に照らして判断する。必要なtoolを使う。結果を正本へ戻す。また次のイベントを待つ。

この構造は、ChatGPTを開いて質問し、回答を受け取って終了するモデルとはかなり違います。目的を持ったAIが存在し続け、必要な時だけ外部世界から起こされるモデルです。

常時動くAIを作ろうとすると、永遠にpollingする仕組みを想像しがちです。しかし実際には、静止している。イベントが来る。起きる。仕事をする。状態を保存する。また静止する、という方が自然です。

人間の組織にも近い構造です。経理担当者は請求書が来たら処理する。レビュアーはレビュー依頼が来たら確認する。運用担当者は障害が起きたら対応する。全員が毎分「仕事はありますか」と確認しているわけではありません。

どこから試すべきか

MCP Eventsの仕様自体はまだDraftで、OpenAI統合にも制限があります。したがって、最初から基幹システムを全面的にイベント依存へするのは早いでしょう。

まず適しているのは、失敗しても回復できる処理、現在pollingしていて無駄が大きい処理、明確な状態遷移がある処理、正本を別に持っている処理です。

逆に、イベントを失ったら重大事故になる処理、順序が完全保証されなければ困る処理、一回しか実行してはいけない不可逆処理、高額な金融取引、外部への重大な公開を、そのままイベントから完全自動化するべきではありません。

最初の実験としてはResearch Meshの一部が扱いやすいでしょう。TaskがREADYになった。イベントを送る。Workerが起動する。結果を保存する。result.createdを出す。Verifierが起動する。ここまでをイベント化する。

Scheduled Taskは残し、一定時間ごとに未処理Taskだけ確認する。イベント経路が安定していることを確認できたら、徐々にpollingを減らす。この順番なら可逆的です。

最後に残す要点

MCP Eventsの本質は、AIをさらに大量に動かすことではありません。必要な時だけ、必要なAIを動かすことです。

第一に、イベントは正本ではなく起動の合図として扱います。起動後の判断はGitHub、Queue、Database、Control Planeなどの現在状態をfresh readして行います。

第二に、イベントは「変化した」ではなく「AIの判断が必要な状態になった」という粒度へ寄せます。

第三に、重複、順不同、再送を前提にし、event IDによる重複排除とidempotentな書き込みを設計します。

第四に、AI自身の変更が再びAIを起動するフィードバックループを防ぎます。

第五に、イベント駆動と時間駆動を対立させません。イベントを通常経路、予定済タスクを整合性確認と復旧経路にできます。

第六に、自動化できることと、自動化すべきことを分けます。公開、重大な変更、金融取引などでは承認境界を残します。

これまでの問いは、「どのAIを何時に起動するか」でした。MCP Eventsによって、問いを変えられます。

システムの中で意味のある状態変化は何か。その変化が起きた時、誰が判断すべきか。判断に必要な正本は何か。どこまで自動で進み、どこで人間へ戻すか。失敗した時、どう回復するか。

Research Mesh、Studio Lab、Kaigo Rules、Repository maintenance、学習、コンテンツ制作は、別々の仕組みに見えます。しかし、状態、イベント、役割、正本、承認境界という観点で見ると、かなり共通した構造を持っています。

MCP Eventsは、この共通構造をChatGPTから扱えるようにするための重要な一歩です。そして今後のAI運用では、「AIに何を頼むか」だけでなく、「どんな出来事が起きた時に、AIが自分から仕事を始めるべきか」が重要な設計問題になっていきます。

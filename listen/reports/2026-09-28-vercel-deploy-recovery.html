Vercel自動デプロイ障害の原因と復旧

このListenでは、rsvp-learningのProductionデプロイが自動化後に一度も成功していなかった原因と、最終的にどの経路で復旧したかを整理します。今回のポイントは、失敗が一つの原因ではなく、段階ごとに別の問題が隠れていたことです。

最初の失敗は依存関係のインストール

定期デプロイの初期workflowでは、依存関係のインストールに npm ci を使っていました。しかし、このリポジトリには package-lock.json がありません。そのため、npm ci は開始直後に終了し、Vercelへ到達する前にデプロイ全体が失敗していました。

通常のテストworkflowは npm install --ignore-scripts を使って正常に動いていました。そこで定期デプロイ側も同じ方式へ揃えました。これにより、依存関係のインストールと npm run check までは通るようになりました。

次に止まったのはVercel CLI

依存関係の問題を直した後、今度は vercel pull で Project Settings を取得できないエラーが発生しました。GitHub Actionsには VERCEL_TOKEN が設定されており、対象Project IDとTeam IDも正しい値でした。

そこでGitHub ActionsからVercelのREST APIへ直接問い合わせ、このtokenで対象プロジェクトを読めるかを確認しました。結果はHTTP 200で、rsvp-learningのプロジェクト情報を取得できました。つまり、tokenそのものやProject IDが間違っていたわけではありません。

scopeを明示してもCLIでは解決しなかった

次に、Vercel CLIへteam scopeとproject IDを明示しました。しかし、CLIは User not found、404という別のエラーで止まりました。REST APIでは正常にアクセスできるのに、CLI経由だけが失敗する状態です。

ここで、CLIの設定解決をさらに追い続けるより、すでに正常に認証できているREST APIをデプロイ経路として使う方針へ切り替えました。

REST APIへ切り替えてProductionまで到達

VercelのDeployment APIへ、GitHubのmainブランチをgit sourceとして渡し、targetをproductionに指定して新しいdeploymentを作成する方式へ変更しました。

最初のAPIリクエストでは、withLatestCommitという項目を不適切に含めていたためHTTP 400になりました。エラーメッセージに従ってその項目を外し、再実行したところ、deploymentの作成に成功しました。その後、READYになるまで状態を確認し、Production deploymentが正常に完了しました。

現在の自動化

現在のworkflowは、mainに前回Productionへ出したcommitから変更があるかを最初に確認します。変更がなければ何もしません。変更がある場合だけ、Vercel projectへのアクセス確認、依存関係のインストール、テスト、Production deploymentの作成を行います。

デプロイがREADYになったら、そのcommitへ vercel-production タグを付けます。次回以降はこのタグとmainを比較して、不要な再デプロイを避けます。

定期実行は6時間ごとです。日本時間では、おおむね午前3時、午前9時、午後3時、午後9時の4回です。これはGitHub ActionsのcronがUTC基準で動くことによるものです。

今回の意味

今回の障害では、最初に見えていた npm ci の失敗だけ直しても、まだデプロイは成功しませんでした。次にVercel CLIの問題が現れ、さらにREST APIへ移した後もリクエスト形式の修正が必要でした。

この経緯から分かるのは、CIやデプロイの障害では、最初のエラーだけを原因と決めつけず、修正後に次の失敗点まで進んだかを確認する必要があるということです。今回は、依存関係、認証、CLI、APIリクエストの各段階を分けて確認したことで、最終的にProductionまで通る経路を確立できました。

最後に残す要点

自動デプロイが失敗していた主な原因は、最初は package-lock.json がないのに npm ci を使っていたこと、その次はVercel CLIでプロジェクト文脈を正しく解決できなかったことです。tokenやProject IDは正常でした。現在はCLIを使わず、Vercel REST APIからProduction deploymentを直接作成する方式に変更し、実際にREADYまで成功しています。

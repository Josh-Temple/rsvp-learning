HTTP・TLSとブラウザからサーバーまで

DNS、接続、TLS、HTTPの各段階をつなぎ、ブラウザの要求がサーバーへ届き応答が返るまでの流れを学びます。

ブラウザは複数段階を通る

ブラウザへURLを入力してから画面が表示されるまでには、名前解決、ネットワーク接続、TLS、HTTP、アプリケーション処理など複数の段階があります。すべてを『Webへつながる』という一つの処理にまとめると、障害箇所を見失います。

代表的な流れでは、まずDNSで接続先のIPを得て、その宛先へ通信を確立し、HTTPSならTLSを使って保護された通信路を作り、その上でHTTPの要求を送ります。

HTTPは要求と応答の意味を定める

HTTPではクライアントがRequestを送り、サーバーがResponseを返します。Methodは要求の意図、Status Codeは処理結果の分類、Headerは制御情報やメタデータ、Bodyは送受信する内容を表します。

HTTPは基本的にStatelessな要求・応答として設計されています。ログイン状態や買い物かごなど継続する状態が必要な場合は、Cookieやアプリケーション側の保存など別の仕組みを組み合わせます。

TLSは通信路を保護する

HTTPSではHTTPをTLSで保護します。TLSは通信内容の機密性と完全性を支え、証明書などを使って接続相手の確認も行います。

ただし証明書が有効だから、そのWebサービスの内容や業務処理まで正しいとは限りません。TLSが主に保証するのは通信路に関する性質であり、アプリケーションの正しさとは分けます。

HTTPの世代で下位方式が変わる

HTTP/1.1やHTTP/2は一般にTCP上で利用されます。一方、HTTP/3はQUICを使い、QUICはUDP上で動きます。したがって『Web通信は必ずTCP』と覚えると現在の構成を説明できません。

同じHTTPの意味を扱っていても、下位層で接続や多重化をどのように実現するかは世代によって異なります。

途中に複数のサーバーが入る

実際のサービスでは、CDN、Proxy、Load Balancerなどが利用者とアプリケーションの間に入ることがあります。利用者が接続したIPが、最終的に処理するアプリケーションサーバーそのものとは限りません。

TLSをどこで終端するか、どこまで暗号化を続けるかも構成によって変わります。障害時は『サーバー』を一台の箱として扱わず、経路上の役割を確認します。

エラーの層を見分ける

HTTPの404が返るなら、少なくともHTTP応答を受け取る段階までは進んでいます。一方、名前解決失敗、接続Timeout、TLSエラーはHTTP処理へ入る前の問題かもしれません。

ブラウザの一つのエラー表示だけで原因を決めず、DNS、IP、TCPやQUIC、TLS、HTTP、アプリケーションという順にどこまで進んだかを確かめます。

この教材の扱う範囲

この章はWeb通信の基礎です。HTTP/1.1、HTTP/2、HTTP/3は下位の通信方式が異なり、CDN、Proxy、Load Balancerなどの構成も環境によって異なります。

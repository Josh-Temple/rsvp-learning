エラー処理と冪等性

この章では、エーピーアイの失敗を扱うためのStatus Code、Retry、冪等性の基本を学びます。

具体例で確かめる

申請APIへ送信した直後に応答がタイムアウトしたとします。サーバー側では作成済みかもしれません。

失敗の種類

エーピーアイ通信は、常に成功するとは限りません。入力が不正な場合があります。権限が不足している場合があります。対象データが存在しない場合があります。

状態コードの役割

サーバー内部で失敗する場合もあります。エイチティーティーピー Status Codeは、失敗の種類を伝えるために使われます。4xxは、要求側に原因がある場合に使われることが多いです。

再試行で起こる重複

タイムアウトは、申請が作られなかった証拠にはなりません。5xxは、サーバー側の失敗を表すことが多いです。失敗時に、何でもRetryすれば良いわけではありません。同じ要求を再送すると、二重登録が起こることがあります。冪等性は、同じ要求を何度行っても、意図した効果が一度のときと同じになる性質です。

エラーを伝える

GETは、通常は副作用を持たないように設計します。重要な登録処理では、Idempotency Keyを使う設計もあります。エラー処理は、正常処理と同じくらい重要です。

同じ要求に識別子を付けて再送し、作成済みなら元の結果を返す設計にします。入力不備、権限不足、サーバー障害では、利用者や呼出し側の対応が異なります。エラー内容と再試行の可否を分けて伝えます。識別子で同じ要求を見分け、再送しても一件の結果へ収束するようにします。

別の条件で確かめる

同じ識別子で、内容の違う申請を再送します。同じ結果として扱うと、どちらを受けたか曖昧です。識別子と要求内容の対応も検査します。

識別子が同じなら無条件に成功を返しますか。内容の不一致は別に扱います。

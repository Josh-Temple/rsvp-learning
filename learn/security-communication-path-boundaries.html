通信経路とセキュリティ境界

架空の申請フォームでURLを入力してから申請が保存されるまでを追います。名前解決、通信の保護、本人の認証、データへの認可、監査ログを、経路上のどこで確かめるか考えます。

通信をData flowとして見る

例えば住民が申請フォームのURLを入力すると、まずDNSで接続先の名前を調べ、その後ネットワークを通ってアプリへ要求を送ります。構成によっては途中にゲートウェイ、プロキシ、負荷分散装置、配信ネットワークのCDNが入ります。アプリは必要に応じてデータベースや外部APIへ接続し、申請を保存します。すべての構成に同じ装置があるわけではありません。

機器の名前だけでなく、送信元、送信先、Protocol、Port、Data種別、認証情報の流れを整理します。

信頼境界はInternetだけではない

申請者の端末からアプリへ入る場所だけでなく、アプリからデータベースへ進む場所やクラウドのアカウント間、管理操作と通常の申請処理の間でも信頼条件が変わります。これらの信頼境界ごとに、誰から何へのアクセスを許すのか確認します。組織の内部にいることだけで無条件に許可してはいけません。

Zero Trustの考え方では、Network上の場所だけを理由に資源を暗黙に信頼しません。

保護と観測を同じ経路へ置く

申請者とアプリの間の通信は適切な区間で暗号化し、アプリでは利用者を認証した上で、その申請を閲覧・変更してよいか認可を確かめます。さらにアプリから保存先へ進む経路でも別の権限を確認します。名前解決の記録、プロキシやファイアウォール、アプリの操作記録、クラウド監査ログは見える事象が異なるため、調べたい異常に応じて監査点を決めます。

Logを大量に集めるだけでなく、どのSecurity判断に使うかを明確にします。

正常経路だけでなく失敗経路を見る

名前解決、認証基盤、ゲートウェイ、外部APIが停止すると、普段の経路を使えないことがあります。そのとき確認を省く抜け道を常設しないようにし、必要な非常用経路にも認証、操作記録、利用期限を設けます。障害時の経路を含めて、構成図にない通信や例外の流れがないか確認します。

構成変更後は図だけでなく、実際の通信と設定を確認します。

短い振り返り

通信は利用者とアプリの間の一本の線ではありません。DNSによる名前解決、経路制御、プロキシやゲートウェイ、アプリからデータベースや外部APIへの接続を含むため、送信元と送信先、データの種類、認証情報の流れを一続きで確認します。

信頼境界はインターネットの出入口だけでなく、サービス同士や管理操作と通常操作の間にもあります。それぞれの境界で認証・認可・暗号化をどう適用するかと、異常をどのログで観測するかを対応付けます。ネットワーク内部という理由だけで信頼は完成しません。アクセスを判断する際には、必要に応じて利用者のIDや端末の状態も確認します。

DNSや認証基盤が停止した場合の非常用経路にも、権限と記録と期限が必要です。構成を変更した後は、図だけでなく実際の通信と設定を照合します。

この教材の扱う範囲

具体的なNetwork構成は環境ごとに異なります。構成図と実際のRoute、Cloud設定、外部Service依存を突き合わせて確認します。

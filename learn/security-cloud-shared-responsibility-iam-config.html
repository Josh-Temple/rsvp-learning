クラウドの責任分界・IAM・設定

クラウドへ移行すると、設備の運用を任せられる範囲は増えます。しかし、情報へのアクセスや設定の安全性まで自動的に保証されるわけではありません。サービスごとの責任と、確認すべき証拠を整理します。

責任分界はサービスごとに変わる

クラウド事業者が保護する設備や基盤と、利用組織が管理する利用者、データ、設定を分けて考えます。IaaSは仮想サーバーなどの基盤を利用する形態、PaaSはアプリケーションの実行基盤を利用する形態、SaaSは完成したソフトウェアを利用する形態です。一般に利用者が直接設定する範囲は違いますが、具体的な責任は契約と各サービスの公式資料で確認します。

例えばSaaSではサーバーへのパッチ適用を事業者が担当していても、誰が文書を外部共有できるかは利用組織の設定次第かもしれません。「事業者が管理しているから安全」という判断はできません。

IAMで人と処理の権限を分ける

IAM、つまり識別情報とアクセス権の管理では、職員のアカウントだけでなく、自動処理が使う権限も確認します。管理者権限を日常作業に使わず、役割ごとに必要な操作を限定します。可能な場合は多要素認証や短期間だけ有効な認証情報を利用し、不要なアクセスキーや使われないアカウントを見直します。

権限が適切かは設定一覧だけでなく、実際の操作権限やアクセス記録でも確認します。強い権限を必要とする緊急時のアクセス、いわゆるブレークグラスについても、誰が使い、事後にどう検証するかを決めます。

公開範囲とデータ保護を確認する

ストレージの公開設定、セキュリティグループ、ネットワーク経路、外部サービスとの連携が組み合わさって、意図しない公開につながることがあります。外部公開された入口を把握し、業務上必要な範囲か点検します。プライベート接続を使う場合も、その経路のアクセス権を確認します。

暗号化は通信や保存データの保護に役立ちますが、許可されていない相手への共有設定まで自動で防ぐわけではありません。鍵やシークレットの管理責任も、利用するサービスの条件に合わせて決めます。

設定のずれを検知する

構成をコードで管理するInfrastructure as Codeや、設定方針をコードで検査するPolicy as Codeは、一貫した管理に役立ちます。ただし、コードが承認済みでも実際の環境が同じとは限りません。手動変更やサービス更新による設定のずれ、つまり構成ドリフトを継続して調べます。

架空の例として、当初は非公開だった保存領域が運用変更で外部公開に変わったとします。設計書を読むだけでは発見できません。実環境の公開範囲の点検と、変更履歴の確認が必要です。

ログと復旧可能性を確かめる

管理操作のログとデータへのアクセスログは、目的とサービスの機能に応じて取得します。攻撃者が同じ権限でログを削除できないよう、権限や保管先の分離も検討します。複数アカウントや環境の分離は役立ちますが、分けただけで侵害の波及が止まるとは限りません。

事業者やリージョンの障害も想定し、バックアップから実際に復旧できるかを試します。ログが取得されていることと、必要な事象を検知できることも別です。検査結果、残る課題、見直す時期を記録します。

設定した事実と効果を分ける

架空の文書保管サービスで、承認済みの設定コードは外部共有を禁止していたとします。しかし、運用担当者が緊急対応で共有設定を変更した場合、コードの審査記録だけでは実際の公開範囲を証明できません。現行のアクセス権、公開設定、変更ログを突き合わせ、差分と変更理由を確認します。

同じ確認方法でも、IaaSでは仮想サーバーの更新やネットワーク設定が利用者の責任となる場合があり、SaaSでは提供者が管理する場合があります。責任を一般論で決めず、契約とサービス仕様に照らします。バックアップの有無だけでなく、権限を失った場合も別の環境で復旧できるかを試し、結果と制約を残します。

短い振り返り

責任分界はサービスの契約と仕様で確かめます。IAM、公開範囲、暗号化と鍵、構成ドリフト、ログ、復旧まで、設定の有無と有効性の証拠を分けて確認することが大切です。

この教材の扱う範囲

責任分界は事業者とサービスごとに異なります。利用するクラウドの契約・公式責任モデル・サービス仕様を必ず確認します。

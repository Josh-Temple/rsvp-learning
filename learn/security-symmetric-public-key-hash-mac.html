共通鍵・公開鍵・ハッシュ・MAC

文書を秘密にしたい、改ざんを見つけたい、送信元を確かめたい。三つの目的によって選ぶ暗号技術は異なります。共通鍵暗号、公開鍵暗号、ハッシュ、MACを具体例とともに区別します。

暗号Primitiveを目的で分ける

暗号技術には、機密性、完全性、真正性など異なる目的があります。共通鍵暗号、公開鍵暗号、Hash、MACを一つの「暗号」としてまとめると、何を守れていないかを見落とします。

例えば文書を第三者に読ませないなら機密性、途中で書き換えられていないか調べるなら完全性、誰が作成したか確かめるなら真正性が問題になります。まず必要な安全性の性質を決め、それを実現する基本技術である暗号プリミティブを選びます。

共通鍵と公開鍵を組み合わせる

共通鍵暗号は同じ秘密鍵で暗号化と復号を行い、大量のDataを効率的に処理しやすい一方、安全に鍵を共有する課題があります。公開鍵暗号は公開鍵と秘密鍵を使い、鍵共有や署名など別の役割を持ちます。

例えば通信相手と安全に共通の鍵を用意する仕組みに公開鍵の技術を利用し、その後の大量の通信を共通鍵で暗号化する方式があります。両者を組み合わせるハイブリッド方式は、目的の違う技術を役割分担させています。

HashとMACを区別する

ハッシュは文書から固定長の値、ダイジェストを計算します。信頼できる元の値と比較すれば変更に気付く助けになりますが、ハッシュを計算すること自体に秘密は使いません。攻撃者も同じ計算ができるため、ハッシュ値だけでは送信者が誰かを証明できません。

一方、MACはメッセージと共有した秘密を使って確認用の値を作ります。秘密を持つ相手が作ったか、途中で変更されていないかを確かめるための仕組みですが、秘密を共有する当事者同士は同じ値を作れるため、公開鍵で第三者が検証できるデジタル署名とは異なります。

認証付き暗号とNonce管理

暗号化しただけでは改ざん検知が十分とは限りません。現代の設計では機密性と完全性を組み合わせる認証付き暗号が利用されます。

認証付き暗号でも、方式によっては毎回の処理に使うノンスや初期化ベクトル、IVを誤って再利用すると安全性が損なわれます。具体的な生成・再利用の規則は方式によって異なるため、暗号ライブラリの仕様に従い、独自の組合せを設計しないことが重要です。

暗号はSystem全体の一部

強いAlgorithmでも鍵が漏れれば意味を失います。暗号化しても認可、Endpoint防御、Backup、監視は必要です。

Algorithmの危殆化や標準変更へ備え、Crypto agility、鍵の所在、Data format、依存Libraryまで把握して移行可能な構成にします。

短い振り返り

暗号技術は何を守るかで使い分けます。共通鍵暗号は大量のデータを効率よく扱える一方で鍵の安全な共有が課題になり、公開鍵暗号は鍵共有や署名などに使われます。実際の通信では目的に応じて両者を組み合わせます。

ハッシュ値は入力の変化を調べる助けになりますが、誰でも計算できるため、それだけでは送信者を証明できません。共有秘密を使うMACとは役割が異なり、MACは公開鍵で検証するデジタル署名とも区別します。暗号化だけで改ざん防止が十分とは限らず、認証付き暗号を選ぶ場合も方式ごとのNonceやIVの規則を守る必要があります。

強い方式を使っても鍵が漏れたり認可が過剰だったりすれば被害は生じ得ます。鍵の保管、端末、バックアップ、監視と組み合わせ、方式の見直しや移行が必要になったときに対応できる構成にします。数学的な方式だけでなく、実装から情報が漏れるサイドチャネルのリスクにも注意します。

この教材の扱う範囲

暗号アルゴリズムを独自実装しません。利用時点で承認されたAlgorithm、Mode、Library、Platform guidanceを確認します。

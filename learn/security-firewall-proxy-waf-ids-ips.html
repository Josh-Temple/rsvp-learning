NIST SP 800-94 Guide to Intrusion Detection and Prevention Systems

Firewall・Proxy・WAF・IDS・IPS

ネットワークの防御装置は、名前が似ていても見ている情報と実行できる制御が異なります。ここでは、各装置の役割を整理し、架空の申請APIを使って、導入した事実と実際の保護を区別します。

どの通信を観測できるか

Firewallは通信の許可や拒否を制御します。送信元、宛先、ポート、通信状態などを条件にできる場合があります。端末側やクラウド側に置かれることもあります。Proxyは通信を仲介する仕組みで、利用者側から外へ接続するForward proxyと、提供側の前段で要求を受けるReverse proxyなどがあります。名称だけで認証や内容検査が必ずできると考えてはいけません。

Web Application Firewall、略してWAFは、主にWebへの要求を検査してアプリケーションの防御を補助します。Intrusion Detection System、略してIDSは侵入の兆候の検知を目的とし、Intrusion Prevention System、略してIPSは配置や方式によって通信の遮断も行います。どの情報まで見えるか、どの制御を実行できるかは製品と設定で変わります。

通信がTLSで暗号化されていれば、復号しない観測点では通信内容を検査できません。TLSがどこで終端されるか、その後の区間で誰がどの情報を見られるかを把握する必要があります。ログが存在するだけで、すべての通信を観測できているとはいえません。

WAFを置いても認可の不備は残る

架空の住民申請APIでは、公開入口にWAFを設置し、ルールが稼働しているとします。職員が申請番号を指定して申請内容を閲覧しますが、もしAPI側でその職員が当該申請を閲覧してよいか確認していなければ、ルールが正常に稼働していても担当外の情報を閲覧できるかもしれません。WAFがWeb上の不審な要求を検査することと、業務上の閲覧権限を決めることは別です。

必要な対策はAPI側のサーバーで申請ごとの認可を確認することです。許可された模擬アカウントと架空の申請データで、担当外の要求が拒否されることを試験します。WAFの遮断ログと、アプリケーション側の拒否記録を区別して確認します。WAFが要求を通したという事実だけでは、アプリ側の認可が正しかったとは結論できません。

迂回、誤遮断、装置故障に備える

防御装置を通らない直接の内部接続や、別のクラウド経路があれば、入口のルールが適用されない場合があります。ネットワーク図だけでなく、実際の通信経路とアクセス権を確かめます。緊急対応で作成した許可ルールには理由、所有者、有効期限を付け、不要な例外を残さないことが大切です。

検知には誤検知も見逃しもあります。正常な申請処理まで遮断された場合の業務影響を試し、検知ログが欠けるなら観測範囲の判断を保留します。装置が故障したとき通信を通すFail openと、遮断するFail closedは、構成によって実際の動作が異なります。安全性だけでなく必要な可用性も考慮し、模擬した障害条件で検証します。

防御装置自身の管理画面、設定のバックアップ、更新、管理者権限も保護対象です。ルールの設定と、意図した通信が止まることは同じではありません。変更のたびに許可・拒否の試験とログ確認を行い、再現できなかった条件を記録します。

短い振り返り

Firewall、Proxy、WAF、IDS、IPSは、対象通信と機能が異なります。暗号化、配置、迂回経路、誤遮断、故障時の動作によって、保護できる範囲が変わります。WAFとAPIの認可を混同せず、設定と実際の拒否記録を分けて検証することが重要です。

この教材の扱う範囲

ここでの申請APIは架空の例です。NIST SP 800-41 Rev.1とSP 800-94は古い技術文書であり、最新製品の機能や動作を一律に保証しません。

認証と認可

この章では、利用者やシステムが誰であるかを確かめる認証と、何をしてよいかを決める認可の違いを整理します。二つは関係していますが、同じものではありません。

まず、認証と認可を分ける

認証は、誰であるかを確認することです。ログインは、その代表例です。パスワードだけで確認する方法もあれば、多要素認証を使う場合もあります。

一方、認可は、何をしてよいかを決めることです。認証が済んでいても、すべての操作を許可してよいとは限りません。ここが、認証と認可を分けて考える重要な点です。

では、ログインできた人なら何でも操作してよいのでしょうか。そうとは限りません。本人であることを確認した後に、その人やシステムに許された操作かどうかを別に確認する必要があります。

ログイン状態をどう扱うか

認証した後、その状態を維持する方法の一つがセッションです。毎回最初からログインし直さなくても、ログイン済みの状態を扱えるようにします。

APIの呼び出しでは、トークンを使って認証する方法もあります。画面上のログインだけでなく、ソフトウェア同士がやり取りするときにも、誰からの呼び出しかを確認する仕組みが必要になります。

OAuthとAPIキー

オーオース、英字では OAuth は、別のサービスへ限定的な権限を委任するために使われます。ここでも、誰であるかの確認と、どこまでの操作を許すかを混同しないことが大切です。

エーピーアイキー、英字では API Key は、呼び出し元の識別に使われることがあります。トークンやAPIキーのような秘密情報は、ソースコードへ直接書かないようにします。

認可と最小権限

認可では、ロールやパーミッションを使うことがあります。つまり、利用者やシステムごとに、許される役割や操作を分けて扱います。

ここで重要になるのが最小権限です。必要な権限だけを与える、という考え方です。認証に成功したことと、広い権限を持つことは別の問題です。

もう一度整理すると、認証は誰であるかを確認し、認可は何をしてよいかを決めます。認証済みでも、許可されていない操作まで実行できるとは限りません。

この章で残しておきたいこと

認証と認可は、一続きの処理に見えても役割が違います。ログイン、多要素認証、セッション、トークンなどは認証を考えるうえで登場します。OAuthによる権限委任や、ロール、パーミッション、最小権限は、何を許可するかという認可の考え方と関係します。

重要な操作ほど、認証と認可の両方を確認します。まず誰なのかを確認し、そのうえで、その操作をしてよいのかを確認する。この二段階を分けて捉えると、認証と認可の違いが整理しやすくなります。

この章は基礎理解用です。具体的な製品仕様、組織固有の工程名、法令上の要件は、この章だけでは確定しません。必要に応じて公式資料や一次資料で確認します。

認証と認可

申請APIの例で、認証と認可の違い、対象ごとの権限確認、トークンとOAuthの役割を学びます。

認証と認可を分ける

申請APIへ利用者Aが入る場面を考えます。Aが誰かを確かめるのが認証で、Aがどの申請へ何をできるかを決めるのが認可です。ログイン済みという事実だけでは、別の利用者の申請を読める理由にはなりません。

権限は「誰が、どの対象へ、どの操作を行うか」で考えます。画面からボタンを隠しても、直接APIを呼ばれる可能性があるため、API側で対象ごとに認可します。

強い認証と広い権限は別

パスワードや多要素認証は本人確認を強めますが、認可範囲まで自動的に広げるものではありません。MFA済みでも、担当外の案件を読めるとは限りません。最小権限では、必要な対象と操作だけを許します。

トークン、OAuth、APIキー

セッションやアクセストークンは認証後の状態やアクセス権限を扱うために使われます。トークンを受け取ったら、有効性だけでなく用途と権限の範囲、対象資源との関係も確認します。

OAuthは、別のアプリへ限定したアクセスを委任するための枠組みです。OAuthのアクセストークンを持つことだけで、最終利用者の本人確認が完了したとは限りません。APIキーも呼び出し元の識別などに使えますが、最終利用者の認証とは分けて考えます。

対象を変えて確かめる

本人確認済みのAがBの申請IDを指定した場合、有効な認証情報があっても、その申請を閲覧する権限がなければ拒否します。所有関係や担当関係と、要求された操作を毎回確認します。

MFA済みなら全件を読めるか、という問いには「認証の強さと認可の広さは別なので、それだけでは読めない」と答えられます。秘密情報はコードへ直接埋め込まず、漏えい時に失効できる運用も用意します。

この教材の扱う範囲

この章は基礎理解用です。具体的な認証方式、トークン形式、権限モデルは利用する仕様とシステム設計を確認します。

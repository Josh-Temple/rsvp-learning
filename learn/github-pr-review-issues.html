Pull Request・Review・Issue

この章では、ギットハブで変更を提案し、レビューし、課題を追跡する基本を学びます。

具体例で確かめる

申請画面の不具合をIssueに記録し、再現手順と期待結果を示します。修正のPRには差分とテスト結果を添えます。

変更を提案する

Pull Requestは、変更を統合するための提案です。変更内容を、差分として確認できます。目的や背景を説明する文章も重要です。Reviewでは、コードや設計の問題を確認します。

レビューで見ること

動作だけでなく、保守性や安全性も見ます。コメントは、具体的な変更箇所へ付けられます。承認条件を、チームで決めることがあります。

Issueと完了条件

Issueの再現条件からPRの試験へつなぐと、何を直したか追えます。Issueは、課題や要望を記録するために使えます。一つのIssueからPull Requestへつなげる運用もあります。何を完了条件とするか明確にします。大きな変更は、小さなPull Requestへ分けると確認しやすくなります。

統合前に確かめる

自動テストの結果も、Review材料になります。Review履歴は、意思決定の記録にもなります。ギットハブは、コードだけでなく変更管理の場として使えます。

レビューで別の入力条件が指摘されたら、修正して確認を受けます。Issueの完了条件に達したかをマージ前に確かめ、PRとIssueを結びつけます。閉じたPRが必ず統合されたとは限らないため、完了の判断は変更の状態も見ます。テスト通過だけで完了にせず、レビューで見つかった別条件と元の完了条件も確かめます。

別の条件で確かめる

プルリクエストの試験は通ったが、元の不具合は残ります。試験条件がIssueの再現条件と違いました。二つを対応させて試験を追加します。

シーアイの緑だけでIssueを閉じられますか。完了条件を実際に確かめます。

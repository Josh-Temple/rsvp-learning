Webhookと非同期処理

この章では、イベント通知、Webhook、Queueなどを使う非同期処理の基本を学びます。

具体例で確かめる

審査完了時に外部システムへWebhookを送るとします。受信側が一時的に停止していれば、後で再送する必要があります。

結果を待たない処理

同期処理では、処理結果を待ってから次へ進みます。非同期処理では、結果を待たずに別の処理へ進めます。時間のかかる処理では、非同期が有効な場合があります。Webhookは、出来事が起きた側から通知する仕組みです。

Webhookで通知する

例えば、決済完了後に通知を送ることができます。通知を受けるユーアールエルを、事前に登録します。Webhookは、同じ通知が複数回来る可能性も考えます。

重複と再試行

Webhookの送信は相手の処理完了を保証しません。そのため、受信側には冪等性が重要です。Queueは、処理要求を一時的にためる仕組みです。送信側と処理側を、時間的に分離できます。再試行や失敗処理を設計しやすくなります。

後から追える記録

一方で、処理状況が見えにくくなることがあります。監視とログが、より重要になります。非同期化は、複雑性と引き換えに柔軟性を得る設計です。

再送で同じ通知が二度届いても、受付番号とイベントIDで重複を判定します。順番が入れ替わる場合は時刻だけでなく状態の遷移を確認します。送信成功と相手の処理完了を同一視しません。イベントIDで重複を見分け、届かなかった通知と順序が逆になった通知を追えるようにします。

別の条件で確かめる

新しい状態の通知が先に届く場合があります。後から古い通知で状態を戻すと誤ります。イベントIDと状態の順序を確認します。

受信時刻だけで最新状態を決められますか。発生順と遷移の妥当性を見ます。

遅延・重複・順序逆転を前提にする

Webhookやキューを使った非同期処理では、通知が遅れたり、同じイベントが複数回来たり、前後の順序が入れ替わったりすることがあります。受信時刻だけで最新状態を決めず、イベントIDや状態遷移を使って妥当性を確認します。

HTTPで受信成功を返したことと、業務処理まで成功したことは別です。再送回数や失敗時の保留先を決め、処理できなかったイベントを後から追えるようにします。

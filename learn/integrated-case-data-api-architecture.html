統合ケース3: データ・API・アーキテクチャ

申請・審査サービスのデータ、正本、API、同期・非同期処理、冪等性、履歴を設計し、画面の裏側で情報がどう流れるかを統合して考えます。

業務上の情報をデータへ落とす

申請を一つの塊にしません。 申請者を分けて考えます。 申請本体も分けます。 添付情報もあります。 審査状態も持ちます。 担当情報も必要です。 関係を明確にします。 重複Dataを減らします。

正本と履歴を設計する

どれが正本か決めます。 派生情報と分けます。 状態変更を履歴に残します。 現在値だけでは足りません。 誰が変えたか残します。 いつ変えたかも残します。 過去時点を再現できるようにします。 監査にもつながります。

APIを契約として考える

APIは画面の裏の契約です。 Requestを定めます。 Responseも定めます。 Errorも定めます。 Versionを意識します。 利用側を突然壊しません。 認証と認可も必要です。 対象単位で権限を見ます。

同期と非同期を使い分ける

即時処理が必要か考えます。 受付番号は即時に返します。 重い集計は後でもよいです。 通知も非同期にできます。 完了前の状態を持ちます。 Queue遅延も想定します。 順序逆転もあり得ます。 完了条件を明確にします。

再試行と冪等性を設計する

通信失敗では結果が不明です。 安全に再試行できるようにします。 Idempotencyを使えます。 処理IDを持たせます。 重複登録を防ぎます。 同じ依頼を識別します。 失敗を成功扱いしません。 結果確認経路を用意します。

障害時の状態を説明できるようにする

DB成功と通知失敗を分けます。 途中成功を想定します。 補償処理も考えます。 一貫性が遅れる場合があります。 画面へ状態を示します。 観測用Logを残します。 障害を追跡できるようにします。 状態の確定点を説明します。

この教材の扱う範囲

この章は概念設計のケースです。具体的なDB製品、API方式、Message Queue製品の選定は扱いません。

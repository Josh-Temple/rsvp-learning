# Daily Paper Listen Workflow

Status: CURRENT  
Updated: 2026-10-01

## 目的

直近の研究・論文から「今日、耳で理解する価値があるもの」を選び、`rsvp-learning` の Listen モードへ安全に追加するための標準手順です。

この文書は、論文探索・選定・検証・Listen化・Repository反映・公開確認までの正本です。

Listen HTMLの実装詳細は `docs/LISTEN_HTML_FORMAT.md`、通常のListen生成ルールは `prompts/listen-generation.md` を優先します。

## 実行環境

日々の実行は、ChatGPTのHuxeプロジェクトから開始することを想定します。

Huxeプロジェクトは実行入口であり、研究内容やRepository状態の正本ではありません。

- 最新の研究情報: 毎回Webからfreshに取得する
- 論文の主要主張: 原論文・正式なproceedings・出版社・研究機関など一次資料を優先する
- Listen実装仕様: このRepositoryの最新版を正本とする
- 現在のRepository状態: mainをfresh readして確認する

過去チャットやMemoryを、現在状態の根拠として扱わないでください。

## 1. Repositoryをfresh確認する

開始時に最低限、次を確認します。

- `docs/DAILY_PAPER_LISTEN_WORKFLOW.md`
- `docs/LISTEN_HTML_FORMAT.md`
- `prompts/daily-paper-listen.md`
- `prompts/listen-generation.md`
- `listen/index.json`
- `package.json`
- 必要に応じて直近のListen research記事

既存の同日・同論文・実質的に重複するListenがないか確認します。

## 2. 候補を探索する

基本探索期間は直近7日程度とします。

24時間以内に限定しません。発表から数日後に重要性が明らかになった研究も候補に含めて構いません。

候補発見には、以下の種類の情報源を組み合わせます。

- Hugging Face Papersなど、研究コミュニティ上の論文発見ページ
- arXiv
- OpenReview
- 学会・conference proceedings
- 学術誌・出版社
- 大学・研究機関・企業研究所のresearch publicationページ
- 必要に応じてPubMed、Semantic Scholar、Crossref等

二次記事、SNS、ニュース、ランキング、コミュニティ反応は「候補発見のシグナル」として利用できますが、それだけを根拠に採用しません。

## 3. 採用候補を絞る

「最も話題の論文」を機械的に選ばず、「今日聞く価値がある論文」を選びます。

次を重視します。

- 新しい知見・方法・能力を示している
- 結果の意味が比較的大きい
- AI、生成AI、AI agents、AI安全性、AI評価、AIガバナンス、科学研究、業務変革などとの関連性が高い
- 方法と比較対象を説明できる
- 主要な主張を一次資料から確認できる
- 研究上・解釈上の限界を説明できる
- 音声で聞くことで理解する価値がある
- 過去のListenと実質的に重複しない

人気、投票数、SNS反応、引用数などは、研究の信頼性そのものとは区別します。

数値スコアだけで採否を決めないでください。採用理由は文章で説明できる状態にします。

## 4. 「掲載なし」を許容する

毎日必ず1本公開する必要はありません。

以下の場合は「本日は掲載なし」で正常終了します。

- 主要候補の根拠確認が不十分
- abstractしか確認できず、強い主張を安全に説明できない
- 既存Listenとの重複が大きい
- 研究としての意味が小さく、日次ノルマのための掲載になってしまう
- 出典や方法に重大な不確実性が残る

掲載頻度より、Listenライブラリの質を優先します。

## 5. 原論文を確認する

採用候補について、可能な範囲で原論文全文を確認します。

最低限、次を分離して把握します。

- 問題設定
- 研究方法
- データ・実験条件
- 比較対象・ベースライン
- 主な結果
- 著者自身の解釈
- 著者が明示する限界
- 外部から見た追加の解釈上の注意点
- 査読済みかpreprintか
- 何が未確認か
- どこまで一般化できるか

abstractだけから、論文本文を超える強い結論を作らないでください。

研究機関や企業の紹介記事を利用する場合も、論文の結果と広報的な説明を区別します。

## 6. Listen原稿を作る

単なるabstractの日本語要約にしません。

耳だけで論旨を追えるよう、概ね次の順序を優先します。

1. この研究の何が面白いのか
2. これまで何が分かっていたか
3. 今回何を調べたか
4. どう調べたか
5. 何が分かったか
6. その結果をどこまで信頼できるか
7. どこから先はまだ言えないか
8. AI・研究・実務にどんな意味を持つ可能性があるか

本文では、次を混同しません。

- 論文で確認された事実
- 著者の解釈
- Listen作成者による分析・示唆
- 推測や未確認事項

煽ったタイトル、過度な一般化、「AIが○○を解決した」のような論文の射程を超える表現を避けます。

## 7. Listen HTMLへ実装する

実装は `docs/LISTEN_HTML_FORMAT.md` に従います。

原則として以下を行います。

- `listen/research/YYYY-MM-DD-<slug>.html` を追加
- 情報基準日を明記
- 出典を本文後に残す
- `listen/index.json` に登録
- 同日複数本の場合もIDとpathを一意にする
- 既存のListen UI・読み上げ操作を壊さない

## 8. 検証する

最低限、Repositoryで定義された検証を実行します。

```bash
npm run check
```

追加したListenについて、少なくとも次を確認します。

- 原論文・一次資料への出典がある
- 出典と本文の主張が対応している
- 情報基準日が分かる
- 事実と分析が分離されている
- 研究上の限界が残っている
- `listen/index.json` のpathと実ファイルが一致する
- Listenの既存テストを満たす

## 9. GitHubへ反映する

掲載する場合は、原則として次までを一連の作業として扱います。

1. mainの最新状態からbranch作成
2. Listen HTMLとindexを更新
3. 検証
4. commit
5. Pull Request作成
6. CI確認
7. 問題がなければmerge

競合、テスト失敗、出典上の問題、重大な不確実性がある場合は、無理にmergeしません。

## 10. production反映を確認する

merge後、現在のRepository運用に従ってproduction deployを行います。

このRepositoryではVercel用workflowが存在するため、必要に応じて手動実行または既存の予定実行を利用します。

「merge済み」と「公開サイトで利用可能」は分けて扱い、可能な場合は公開反映まで確認します。

## 11. 完了報告

通常の完了報告は簡潔にします。

掲載した場合:

- 論文名
- 採用理由
- 最も重要な結果
- 重要な限界
- PR / merge状態
- production反映状態

掲載しなかった場合:

- 主に確認した範囲
- 掲載なしとした主要理由

候補一覧を大量に並べる必要はありません。

## 日次の短い実行指示

Huxeプロジェクトからは、原則として次だけで開始できます。

> Daily Paper Listenを実行してください。Repositoryとworkflowをfresh readし、今日聞く価値のある論文をfresh調査してください。採用基準を満たすものがあれば、一次資料を確認してListenへ実装し、検証、PR、CI確認、merge、production反映確認まで進めてください。十分な候補がなければ無理に掲載しないでください。

## V-1 Secure by Design / Secure by Default

**仮Lesson ID（未採番）:** `security-secure-by-design-default`  
**計画上の位置:** Course V / 1章目  
**到達目標:** 新しい行政申請サービスの設計案を見て、設計上の欠陥と設定不備を区別し、何を安全な初期状態とするか、検証に必要な証拠は何かを具体的に説明できる。

**前提:** I-2（資産と信頼境界）、I-6（脅威モデリング）、I-7（管理策の有効性）、III-4（認可・最小権限）、IV-7（クラウドの責任分界）。

### 本文（Learn用の連続講義・第一試案）

安全なシステムを作るというと、完成したアプリケーションを検査し、危険なところを修正する作業を思い浮かべるかもしれません。しかし、検査する以前に決めておかなければならないことがあります。そもそも、誰がどの情報を見られる設計なのか。異常な操作を受けたとき、どの状態に戻るのか。利用者が設定を変えなくても、危険な操作を避けられる初期状態になっているか。これらは後から脆弱性を探すだけでは十分に補えません。

Secure by Designは、守るべき資産と想定する利用方法を確認し、必要な安全対策を設計に組み込む考え方です。Secure by Defaultは、導入直後に特別な操作をしなくても、できるだけ危険な状態を作らない初期設定にする考え方です。前者は「何を満たすべき設計にするか」、後者は「利用者が最初に使う状態をどうするか」に重点があります。両方は関連しますが同じ意味ではありません。

ここでは、住民がオンラインで申請し、担当職員が内容を確認するサービスを考えます。これは架空の例です。申請書には氏名や連絡先が含まれ、担当部署によって閲覧できる範囲が異なるとします。ある設計案では、ログインしている職員なら申請番号を指定してどの申請も閲覧できるようになっています。この場合、問題は画面の見せ方だけではありません。申請番号が分かることと閲覧権限を持つことは別であり、サーバ側で部署や職務と対象申請の関係を確認する仕組みが必要です。画面上でリンクを隠しても、この欠陥は解消しません。

さらに、導入直後から管理機能を広く公開し、担当者が必要に応じて制限を有効にする初期設定になっていたとします。設計段階で管理者が必要とする機能を選定することと、最初から全員に使える状態で提供することは違います。安全な初期状態を考えるなら、不要な機能や高権限を初めから与えず、必要になった場合に権限を確認して追加する運用を検討します。ただし、安全側へ寄せれば何でもよいわけではありません。緊急時に業務が停止する可能性、利用者の権利、正規業務への影響も合わせて確認します。

では、設計が安全だと、どう確かめればよいでしょうか。図面に「最小権限」と書いてあるだけでは分かりません。資産と利用者の種類を列挙し、許可される操作と拒否される操作を決め、担当部署の異なるテスト用アカウントで想定した境界が守られるか確かめます。初期設定を用いた新規導入の検査も必要です。権限変更や異常処理の記録を残し、開発時のテストと運用時の監視をつなげます。

重要なのは、設計・実装・設定・運用を一つの言葉でまとめないことです。安全な設計でも実装ミスは起こり、適切な実装でも初期設定や運用を誤れば事故につながります。必要な対策を設計に書き、その実装と初期設定が正しいかを別々の証拠で確かめることが、学習者に求める判断です。

### 理解確認問題（レビュー待ち）

**Q1（区別・短答）** 「画面上の申請リンクを非表示にしたので、部署外の職員は申請を読めない」という説明の問題点は何か。

- 模範解答: 画面のリンク制御とサーバ側の閲覧権限検証は別。認証済みの職員であっても、対象申請ごとに認可を確認する必要がある。
- 誤答例: 「ログイン機能があれば十分」→ 認証と認可の混同を示す。
- 測定: 権限境界の設計判断。関連 III-4、V-4。

**Q2（設計と初期設定の比較）** 標準で不要な管理機能を有効にしている製品と、利用時に管理者が明示的に有効化する製品を比較する際、何を確認するか。

- 模範解答: 初期権限と露出する機能、正規業務への影響、必要時に権限を追加する手順、初期状態の検査証拠。単純に後者だけが絶対に安全と断定しない。
- 誤答例: 「初期設定を厳しくすれば他の検証は不要」→ 実装不備や運用での変更を見落としている。
- 測定: Secure by Defaultの適用条件と限界。

**Q3（ケース）** 導入直後の試験で部署外の閲覧ができなかった。これだけで本番の安全性を保証できるか。

- 模範解答: 保証できない。対象と権限の組合せ、設定の変更、異常系、ログ、運用時の監視、継続的な再評価を確認する。試験環境と本番環境の差も検討する。
- 誤答例: 「テストが一度通れば設計上の問題は解消」→ 試験範囲と有効性の継続確認を混同。
- 測定: 検証の証拠と限界。

**RSVP化で残す概念:** 設計段階での制御、初期状態、認証/認可、サーバ側検証、機能・権限の最小化、業務影響、設計と実装・運用の証拠。英語専門用語は意味を失わずに表示し、無理に24文字以内で途中切断しない。

**主な出典候補:**

- [OWASP Top 10:2025 A06 Insecure Design](https://top10.owasp.org/2025/A06_2025-Insecure_Design/)
- [OWASP Top 10:2025 introduction](https://top10.owasp.org/2025/0x00_2025-Introduction/)
- [NIST SP 800-218 SSDF v1.1 final](https://csrc.nist.gov/pubs/sp/800/218/final)
- [CISAほか Secure-by-Design and -Default原則公表（2023-04）](https://content.govdelivery.com/accounts/USDHSCISA/bulletins/354a744)

**人間レビュー項目:** 適用するサービスの業務要件、想定ユーザー区分、初期設定の具体性、過度に断定していないか、仮想ケースの説明の自然さ、正式な用語の読み方。

## V-2 入力・出力・Injection

**仮Lesson ID（未採番）:** `security-input-output-injection`  
**計画上の位置:** Course V / 2章目  
**到達目標:** 外部入力を受け取るアプリケーションの処理を見て、入力検証、命令とデータの分離、表示先に合わせた出力対策を区別し、失敗条件と効果の確認方法を説明できる。

**前提:** V-1、I-2（信頼境界）、III-8（データの分類）、IV-2（Web通信の基礎）。V-3ではブラウザ上のXSS等をより詳しく扱う。

### 本文（Learn用の連続講義・第一試案）

アプリケーションは、利用者が入力した文字、外部サービスの応答、保存済みの文書などを受け取って処理します。ここで重要なのは、「画面に表示されたデータだから安全」「自分たちのデータベースにある情報だから信頼できる」とは限らないことです。いったん外部から入った情報が保存された後でも、次の処理では信頼できない入力として扱う必要がある場合があります。

Injectionとは、本来はデータとして扱うはずの入力が、別の命令や解釈の一部として処理され、意図しない動作を生む問題です。SQL、OSコマンド、テンプレートなど、データを受け取る処理系によって何が危険かは違います。あらゆる入力を禁止するのではなく、どこで命令が組み立てられるのかを調べることが出発点です。

例えば、申請一覧を検索する機能を考えます。担当者がキーワードを入力すると、サーバはデータベースで条件に合う申請を探します。危険なのは、入力文字列をそのまま検索命令へ継ぎ足し、キーワードが命令の構造に影響できる状態です。より安全な設計では、検索命令の構造と検索する値を分離し、データベースのパラメータ化されたインターフェースを使います。検索文字列の長さや形式を検証することも有用ですが、検証だけで命令とデータの分離の代わりになるとは限りません。

これに対して、検索結果をブラウザで表示する場面では、別の注意が必要です。利用者から受け取ったコメントに、画面側の処理を変えてしまうような文字列が含まれる場合があります。保存時の検証が一部を通過したとしても、表示先がHTML本文なのか、属性なのか、URLなのかによって必要な対策は異なります。原則として文字列はコードとして実行させず、画面に表示する単なるテキストとして扱います。構造化されたリッチテキストを許す場合は、用途に合ったサニタイズなど別の検討が必要です。

つまり、入力検証、命令とデータの分離、出力先に応じた符号化・サニタイズは、どれか一つを導入すれば他を置き換えられる関係ではありません。入力検証は「必要な形式や範囲か」を確認し、安全なインターフェースは「文字列が命令へ変わらないか」を制御し、出力時の対策は「表示する場所で意図しない動作が起きないか」を守ります。データが通る経路のそれぞれで役割を整理します。

効果を確かめるときには、危険な文字列をただ一種類試すのではなく、処理される文脈と期待結果を決めます。検索では入力がデータとして扱われること、画面表示では文字列がコードではなくテキストとして出ること、異常な入力が適切に拒否・処理されることを、安全なテストデータで確認します。変更のたびに回帰検査を行い、実装言語や表示ライブラリを変更した場合は前提を見直します。

最後に、セキュリティ対策は万能ではありません。パラメータ化しても、利用者の閲覧権限が誤っていれば他人の申請を取得できるかもしれません。画面の表示対策が正しくても、外部APIへの過剰な権限を防げるわけではありません。境界を一つずつ確認し、別の章で学ぶ認可やセッションの対策と組み合わせて判断します。

### 理解確認問題（レビュー待ち）

**Q1（概念の区別）** 入力欄で一部の特殊文字を拒否する処理を設けた。これだけでSQL Injection対策が完了したと判断してよいか。

- 模範解答: よくない。入力検証だけでは十分な保証にならない。SQL命令と値を分離するパラメータ化された問い合わせ等を検討し、その使用箇所と回帰テストを確認する。
- 誤答例: 「特殊文字を拒否したので必ず安全」→ 入力ルールに依存し、処理系での解釈を見落としている。
- 測定: 検証と命令・データ分離の差。

**Q2（条件変更）** 同じ文字列を検索条件としてSQLに渡す場合と、ブラウザのHTML本文に表示する場合、同じ対策を流用できるか。

- 模範解答: 対象が違うので、そのまま流用できない。SQLではパラメータ化、HTMLでは文字列を実行せず表示するための文脈に適した符号化等を考える。
- 誤答例: 「HTML用に符号化すればSQLも安全」→ 出力先の文脈とDB命令の解釈を混同している。
- 測定: 出力文脈と処理系の区別。

**Q3（失敗条件）** DB検索にパラメータ化を導入し、画面側の出力処理も安全にした。本人の権限外の申請が検索結果に出た場合、何を点検するか。

- 模範解答: サーバ側の認可、検索条件に含まれる所有者・部署などの制約、権限変更後の反映、ログとテスト対象を点検する。Injection対策と認可制御は別。
- 誤答例: 「Injection対策があるのでアクセス制御は不要」→ 異なる脆弱性を同一視している。
- 測定: 防御の組合せと残存リスク。

**RSVP化で残す概念:** 非信頼入力、SQL等の処理系、命令とデータの分離、パラメータ化、入力形式の検証、HTML表示文脈、出力時の対策、権限検証、回帰テスト。誤読を招く英数字途中切断は禁止。

**主な出典候補:**

- [OWASP Top 10:2025 A05 Injection](https://top10.owasp.org/2025/0x00_2025-Introduction/)
- [OWASP Injection Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Injection_Prevention_Cheat_Sheet.html)
- [OWASP SQL Injection Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html)
- [OWASP Cross Site Scripting Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html)

**人間レビュー項目:** Injectionの定義範囲、SQLの説明の厳密さ、ブラウザでの表示文脈ごとの対策、実装・言語依存性、用語の読み上げ方、安全な教育ケースとしての適切性。

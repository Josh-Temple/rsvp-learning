Secure by Design / Secure by Default

安全なシステムを作るときは、何を許すかを決める設計、その規則を動かす実装、導入した直後の設定、変更後も保護を続ける運用を区別します。この章では架空の自治体申請サービスを使い、問題の原因を見つけ、対策を比較し、どの証拠があれば判断できるかを考えます。拒否を増やすことだけが目標ではありません。許可された申請と審査が、必要な保護の下で成功することも確かめます。

安全な設計と初期状態の関係

Secure by Design、セキュア・バイ・デザインは、顧客の安全を開発前から設計の目標に置く考え方です。守る情報と想定する脅威を整理し、必要な制御をシステムの構造へ組み込みます。Secure by Default、セキュア・バイ・デフォルトは、その中でも利用を始めた直後の安全に注目します。顧客が追加の設定をしなくても、よくある脅威への防御が有効になる標準を作ります。安全な初期設定は安全な設計の一部であり、対立する二つの方式ではありません。共同ガイドは基本的な防御を追加料金の選択肢にせず提供することも勧めています。ただし、安全な設計でも欠陥は残り得ます。無事故を保証する言葉ではありません。

例えば、認証済みなら全申請を読める仕様では、認証の実装が正確でも担当外の閲覧を止められません。誰がどの申請を読めるかという規則が必要だからです。設計では業務規則と適用する構造を決め、実装では各処理にその規則を働かせます。初期設定では導入時に制御が有効かを決め、運用では異動や設定変更の後も保護を保ちます。この区別は修正箇所を探す手掛かりです。現実の問題が必ず一段階だけに収まるという意味ではありません。

架空サービスの資産と役割を決める

青波市オンライン申請には、住民の氏名、連絡先、申請理由、添付書類が入ります。情報が漏れること、不正に書き換えられること、申請を受け付けられなくなることを考えます。このサービスでは住民は自分の申請を読み、提出前に修正できます。職員は現在の担当部署の申請を審査します。設定管理者には申請本文を読む権限を自動で付けません。委託事業者は承認された期限付きの診断情報を扱い、申請書を常時取得する権限は持ちません。ここまでの役割規則は教材の前提であり、全自治体やすべての製品に共通する規則ではありません。

この前提を変えると判断も変わります。代理申請を導入するなら、本人だけに許可する規則では正規の代理人まで拒否してしまいます。委任の対象と期限、取消の反映を定め、その条件で許可と拒否を試します。設定管理者が実際には審査も兼務する場合も、仕事に必要な範囲を明示して付与します。役割名から無制限の権限を推測したり、業務前提の変更を個別例外だけで隠したりしません。

認可をすべての取得経路へ適用する

認可規則には、要求した主体と操作だけでなく、対象の申請、読んだり変更したりする項目、申請の状態も含めます。自分の申請でも、提出後の変更はこのケースでは許しません。サーバ側で認証済みの主体情報と現在の権限を確認し、申請の属性と照合します。画面から渡された部署名を本人の権限として信用しません。ボタンの非表示や推測しにくい申請番号は、認可の代わりではありません。画面を経由しない要求もサーバへ届くからです。

詳細画面だけで拒否しても、一覧、添付取得、一括出力が同じ規則を使っていなければ、別の経路から情報が出ます。認可を共通の処理にすると漏れを減らせますが、各経路が実際にその処理を呼ぶ証拠が必要です。保護する操作は原則として拒否し、明示した条件を満たす場合だけ許可します。一方、一般向けの案内ページは匿名閲覧を明示した別の規則で扱えます。全機能にログインを要求するという意味ではありません。

担当情報を取得できず認可を判断できない場合は、保護対象の要求を許可しません。ログインできたことだけで担当範囲は証明できないためです。欠落した部署同士を同じ担当とは判断しません。空文字や空白も無効な部署識別子として扱います。この例は教材で定めた部署一覧を使い、双方の識別子を確認してから照合します。その一覧への一致だけで、実際の所属や情報の最新性まで証明できるわけではありません。住民の本人申請は部署によらない別の規則で許可します。障害中に全申請の取得を自動許可する方式は、このケースの情報保護要件を満たしません。ただし拒否を続けるだけでは申請業務も止まります。再試行の案内、承認された代替窓口、復旧後の処理を別に設計し、その窓口の権限と業務の成功も確認します。

最小権限を業務と一緒に検証する

最小権限では、仕事に必要な操作と対象を、必要な期間だけ許します。全員を拒否することではありません。青波市では設定変更と申請本文の閲覧を分け、担当職員の審査が成功することも試します。検索用のDB接続に表の作成や削除を付けない判断もできます。ただしDB権限を絞っただけでは、住民ごとの閲覧制御は完成しません。共通のDB利用者で接続していても、アプリケーションが元の要求主体を認可する必要があります。

職務ごとに役割を割り当てるRBACを基本にし、担当部署や申請状態も条件にするなら属性を使う規則と組み合わせられます。その場合は属性の正確さと更新が前提です。複雑な規則を増やせば安全になるわけではありません。許可と拒否の理由を説明でき、変更時にも保守できる方式を選びます。管理者が兼務する必要があるなら、根拠と範囲を明示し、名称上の役割分離だけで安全とは判断しません。

導入直後の状態を試す

安全設定が手順書にあっても、導入直後に申請が匿名公開されるなら、このケースの安全な標準にはなっていません。追加の手動変更をする前の新規環境を試します。候補の初期状態は、申請保管先が非公開、委託支援のアクセスが無効、共通の管理者初期パスワードを配らない状態です。初回管理者を限定した経路で登録し、管理操作には多要素認証を求めます。監査に必要な操作記録も有効にしますが、申請本文や秘密値は記録しません。記録を読める人と保存期間も決めます。これらは本ケースの設定案であり、すべての製品で同じ値が最適だという主張ではありません。

設定ごとに、目的、初期値、変更方法、安全性と業務への影響、他の設定との依存を記録します。例えば非公開化によって、本人の提出や担当職員の取得まで止まれば、規則に合う方法へ直す必要があります。安全性を緩める変更には理由と補完策、承認を残します。設定例を採用したことと、その環境で有効性を試したことは別です。運用では基準と実際の設定を照合し、変更の差分と復元手順も確認します。

権限の終了と非常時を忘れない

職員が異動したのに、ログイン時の部署だけで判定すると、旧部署の閲覧権限が残る場合があります。本ケースの機微情報では旧権限の継続を許さず、要求時に現在の担当を確認します。キャッシュや長寿命の資格情報を使うなら、失効の伝わり方と遅延を別に検証します。単体試験で現在の属性を読めても、分散処理や、判定後に担当が変わる競合まで確認したことにはなりません。実環境相当の統合試験が必要です。後で記録を見て権限を取り消しても、既に開示した情報は取り戻せません。

委託先への支援アクセスも、承認した対象、終了時刻、責任者を明らかにします。診断情報は氏名を消しただけで安全とせず、再識別や秘密値の混入も確認します。期限前の瞬間は、支援が有効で活動中の委託先、承認済みの主体と申請、許された診断項目がそろう場合に限り許可されます。期限ちょうどと期限後に拒否され、不要な権限が除去されるところまで確かめます。夏時間の終了で現地時計の表示順と実際の瞬間の順序が逆転する場合もあります。UTCに換算した瞬間の順で比べ、同じ瞬間なら別の時差表現でも結果を変えません。これは架空モデル内の認可判断です。分散環境の失効や資格情報の破棄まで確認したものではありません。非常時に特別権限が必要なら、発動条件、対象、時間、承認者を決め、操作記録と利用後の見直しを行います。常時の全件公開で非常時の手続きを代用しません。承認済みの代替窓口が業務を果たせるかも試します。

原因に合う対策を比較する

担当外の閲覧を止める規則がなければ、設計の欠落を直します。規則があるのに添付APIが検査を呼ばなければ、実装の適用漏れを直します。検査が設定で無効なら、初期設定や運用変更も調べます。同じ漏えいという結果でも修正箇所が違います。設計が欠けたままコードの書き方を整えても必要な制御は生まれません。WAFや暗号化の追加も、誰に許すかという認可の誤りを直接は直しません。

画面だけで担当を制限する案は、直接の要求に対応できません。サーバで申請ごとに検査する案は、各取得経路への適用と属性更新を確認する必要があります。DBの行単位制限を加える案には、DBへ要求主体を安全に伝え、再利用する接続で主体が混ざらないようにする設計が必要です。行制御という機能名だけでは安全を保証できません。本ケースではサーバ側の認可を基本にし、DBでの追加制限は別の設計レビューで判断します。層を増やすときも、各層の前提と保守担当を確認します。

判断を支える証拠をそろえる

業務規則と権限表は守る意図の証拠です。適用設計とコードは実現方法の証拠です。初回起動の設定と実際の試験結果は、導入時の動作を確認する材料です。架空アカウントと申請データで、自分の申請は取得でき、他人の申請は拒否されることを対で試します。まず業務の条件を変えます。担当部署の内外と提出前後で、許可と拒否が規則に合うか確認します。部署の欠落、空文字、空白でも拒否を確かめます。次に取得経路を変え、詳細と一覧、添付と一括出力を検査します。変更や障害への対応も試します。異動後と委託期限後の拒否を確かめ、認可情報が取れない場合の期待結果も定めます。使用した版、条件、結果を記録し、観測できる操作ログと対応させます。ログがないだけでは事故がないとはいえず、ログがあっても拒否処理の代わりにはなりません。

提供者には安全な実装と初期設定を作り、改善と説明を続ける役割があります。運用者には業務規則と変更を管理する役割があります。委託契約では、どの作業を誰が行い、どの証拠を残すかを明示します。「任せた」というだけでは責任は整理できません。一方、共同ガイドの提供者責任は、運用者の責任が消えるという意味ではありません。法的な責任や個別契約への適合は、この架空教材では判定していません。

短い振り返り

システムを見るときは、まず業務で守る規則を明らかにし、次に実装と初期状態へその規則が届いているかを確かめます。変更後にも許可と拒否が正しく働き、必要な業務が続くかを見ます。設計書や設定一覧だけで完了にせず、対象と条件に合う実行証拠を選ぶことが判断の軸です。

この教材の扱う範囲

ローカル例は架空規則の一部を試す教育用モデルです。実サービスの全取得経路、初回登録、多要素認証、設定の変化、分散した権限失効まで検証していません。業務や役割が変われば規則と試験を見直します。未検証の条件から安全を推測しません。

制作状況：自己査読や問題の用意は、独立受入や実受講者の理解を測った結果ではありません。新しい候補SHAの独立内容審査と、実音声・実機QAは別に必要です。詳細は検証記録に保存しています。

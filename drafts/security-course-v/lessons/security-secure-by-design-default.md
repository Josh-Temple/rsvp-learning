# Secure by Design / Secure by Default

Status: DRAFT v0.1
Publication: HOLD
Created: 2026-10-11

## 学習目標

- 仕様、実装、初期設定、運用変更の証拠から、問題が発生した段階を特定し、その段階に合う修正を選べる。
- 主体・操作・申請・項目・状態を含む認可規則を作り、許可と拒否の両方の期待結果を説明できる。
- 権限縮小や安全な初期設定の案を、情報保護、正規業務、責任者、例外の終了条件から比較できる。
- 設計書、コード、初回起動の設定、試験結果、変更記録の違いを説明し、足りない検証を指摘できる。

## 前提と既存教材との接続

I-2の資産・依存関係と信頼境界、I-6の脅威モデリング、III-1の認証と認可の区別、III-4のRBAC・ABAC・最小権限・特権管理、III-8のデータ分類、IV-7の共有責任を前提とする。役割名や契約名だけでは安全を判定できない理由を、設計から運用までの証拠へつなぐ。V-2では、この認可とは別に、データを命令へ変えてしまう実装上の問題を扱う。

## ケースの前提

架空の「青波市オンライン申請」。住民は自分の申請を読み、提出前に修正する。職員は現在の担当部署の申請を審査する。設定管理者には申請本文を読む権限を自動付与しない。委託事業者は承認された期限付きの診断情報だけを扱う。代理申請は未導入。これらは教材の業務規則であり、行政一般の法的義務や全システム共通の役割規則ではない。

## 本文

### 安全をどの段階で作るか

1. 安全なシステムかを判断するには、
2. 設計から運用まで証拠をたどります。
3. 認証が成功したことだけでは、
4. 全申請の閲覧を許せません。
5. 何を誰に許すかが未定なら、
6. 実装者は認可を正しく作れません。
7. Secure by Designは、
8. 顧客の安全を設計の目標に置きます。
9. 開発前に資産と脅威を考え、
10. 必要な制御を構造へ組み込みます。
11. Secure by Defaultは、
12. 安全な初期設定を標準にします。
13. 利用開始時の追加作業に頼らず、
14. よくある脅威への防御を備えます。
15. 安全な初期設定は安全な設計の一部です。
16. 基本的な防御を追加料金の選択肢にせず、
17. 初期状態から提供することを勧めます。
18. 二つを対立する方式とは考えません。
19. 安全な設計でも欠陥は残り得ます。
20. 無事故の保証ではありません。
21. 製品提供者が安全を顧客へ丸投げせず、
22. 改善と説明の責任を負う考え方です。
23. 運用者の責任が消える意味ではありません。
24. この章は四つの段階を区別します。
25. 設計は、守る規則と構造を決めます。
26. 実装は、その規則を処理にします。
27. 初期設定は、導入時の状態を決めます。
28. 運用は、変更後も制御を維持します。
29. 段階の区別は修正箇所を探すためです。
30. 現実には互いに影響します。

### 守る対象と業務を先に決める

31. 青波市の申請には氏名と連絡先、
32. 申請理由と添付書類を保存します。
33. 漏えいだけでなく不正変更や、
34. 申請を受け付けられない状態も考えます。
35. 住民、職員、管理者、委託先の間で、
36. 情報を渡す境界を明らかにします。
37. この例では住民は自分の申請を読みます。
38. 修正できるのは提出前までです。
39. 職員は現在の担当部署の申請を審査します。
40. 設定管理者でも申請本文は読めません。
41. 委託先は期限付きの診断情報を扱います。
42. 生の申請書を常時取得する権限はありません。
43. これは架空サービスの業務規則です。
44. 全自治体の共通規則ではありません。
45. 代理申請を導入する場合には、
46. 本人だけという規則を変える必要があります。
47. 委任の範囲と有効期限を設計し、
48. 取消後の拒否も試験します。
49. 業務前提の変更を例外の乱立で隠しません。

### 認可規則を要求ごとに働かせる

50. 認可は主体と操作だけでは足りません。
51. 対象申請、項目、申請状態も指定します。
52. 同じ住民でも別の人の申請は拒否します。
53. 自分の申請でも提出後の修正は拒否します。
54. 職員の審査権限は、
55. 全部署の申請を読む権限ではありません。
56. 認証済みの主体情報を使い、
57. サーバ側で現在の権限を評価します。
58. 画面から渡された部署名を、
59. 本人の権限として信用しません。
60. 申請番号が推測しにくくても、
61. 閲覧権限を確認する代わりにはなりません。
62. ボタンを隠すだけでも不十分です。
63. APIへ直接届く要求も確認します。
64. 保護する操作は原則として拒否し、
65. 明示した条件を満たすときだけ許可します。
66. 公開する案内ページは、
67. 匿名閲覧を明示した別の規則で扱えます。
68. 全機能へのログイン強制を意味しません。
69. 一覧、詳細、添付の取得、出力でも、
70. 同じ認可規則が働くか確認します。
71. 一括出力だけ検査を省くと、
72. 詳細画面の拒否を回避できてしまいます。
73. 認可の共通処理は漏れを減らせますが、
74. 各経路が呼び出す証拠も必要です。
75. 認可判断に必要な情報を取得できないとき、
76. 保護対象への要求は許可しません。
77. 自動許可に切り替えて復旧を装いません。
78. 利用者へ再試行や承認済みの代替窓口を案内し、
79. 業務継続も別に設計します。

### 最小権限と正規業務を両立させる

80. 最小権限は必要な操作と対象を、
81. 必要な期間だけ許す考え方です。
82. 全員を拒否すれば業務を果たせません。
83. 担当職員の審査は成功すべきです。
84. 管理者に全権限をまとめると、
85. 設定変更と情報閲覧の被害が重なります。
86. この例では設定の管理権限と、
87. 申請本文の閲覧権限を分けます。
88. 実際の業務で兼務が必要なら、
89. 明示的な付与根拠と監査を設けます。
90. 役割を分けたという名称だけでは、
91. 分離の動作証拠にはなりません。
92. DB接続用の権限も絞ります。
93. 通常の検索処理に、
94. 表の作成や削除の権限を与えません。
95. ただしDB権限を絞っただけでは、
96. 住民ごとの閲覧制御は完成しません。
97. 共通のDB利用者で接続する場合も、
98. アプリの要求主体を認可します。
99. RBACは職務ごとの役割に向きます。
100. 担当部署や申請状態も条件にするなら、
101. 属性を使う規則と組み合わせられます。
102. 属性の正確さと更新が前提です。
103. 複雑な規則ほど安全とは限りません。
104. 保守できる規則を選び、
105. 許可と拒否の理由を説明できるようにします。

### 安全な初期状態を確かめる

106. 手順書に安全設定が書いてあっても、
107. 初回起動が危険なら安全な標準とはいえません。
108. 新規導入した環境を、
109. 追加の手動変更なしで確認します。
110. この例では申請保管先を非公開にし、
111. 委託先の診断アクセスを無効にします。
112. 管理者の共通初期パスワードは配りません。
113. 初回管理者の登録を限定した経路で行い、
114. 管理操作には多要素認証を求めます。
115. 監査に必要な操作記録を有効にします。
116. 記録には申請本文や秘密値を含めません。
117. 記録の閲覧権限と保存期間も決めます。
118. これらは本ケースの初期設定案です。
119. 全製品で同じ値が最適とは限りません。
120. 設定ごとに目的、初期値、変更方法と、
121. 安全性と業務への影響を記録します。
122. 設定間の依存も確認します。
123. 安全性を緩める変更には、
124. 理由と補完策を示して承認を得ます。
125. 設定例を採用しただけで、
126. 個別の脅威を防げたとは判断しません。

### 異動、委託、非常時を設計する

127. 職員が別部署へ異動したら、
128. 旧部署の申請を読めなくする必要があります。
129. ログイン時の部署を保持するだけでは、
130. 古い権限が残る場合があります。
131. この例では現在の担当を要求時に確認します。
132. キャッシュや長寿命の資格情報があるなら、
133. 失効の反映経路と遅延を別に検証します。
134. 本ケースの機微情報は、
135. 旧権限の継続を許さない要件です。
136. 単体試験だけでは分散処理や、
137. 判定後の競合を検証できません。
138. 実環境相当の統合試験が必要です。
139. 委託先の支援は承認した対象に限定し、
140. 終了時刻と責任者を記録します。
141. 診断情報も再識別や秘密の混入を確認します。
142. 単に氏名を消しても安全とは限りません。
143. 期限後の拒否と権限の除去まで確認します。
144. 非常時の特別権限が必要なら、
145. 発動条件、対象、時間、承認者を決めます。
146. 操作を記録し、利用後に見直します。
147. 常時の全件公開で代用しません。
148. 代替窓口も業務目的に合わせて検証します。
149. 安全な初期値を設けても、
150. 運用変更で保護が失われ得ます。
151. 設定変更の承認、差分検査、復元手順を設け、
152. 実際の設定と基準を照合します。

### 欠陥の原因から対策を比較する

153. 担当外の閲覧を止める規則がないなら、
154. 設計の欠落です。
155. 規則があるのにAPIが検査を呼ばないなら、
156. 実装の欠陥です。
157. 検査が設定で無効になっていれば、
158. 初期設定や運用変更も調べます。
159. 同じ漏えいでも修正箇所は違います。
160. 設計が欠けたまま実装を整えても、
161. 必要な制御は生まれません。
162. WAFや暗号化を追加しても、
163. 許可対象の誤りを直接は直せません。
164. 第一案は画面だけで担当を制限します。
165. 直接の要求を防げないため採用できません。
166. 第二案はサーバで申請ごとに検査します。
167. 各経路への適用と属性更新が課題です。
168. 第三案はDBでも行単位に制限します。
169. DBへ主体を安全に伝える設計と、
170. 接続再利用時の分離が必要になります。
171. 行制御を導入すれば常に安全になる、
172. という意味ではありません。
173. この例では第二案を基本にし、
174. 第三案は別の設計レビューで判断します。
175. 防御の層を足すときも、
176. 各層の前提と保守責任を確認します。

### 証拠をそろえて判断する

177. まず業務規則と権限表を示します。
178. 次に規則を適用する設計とコードを示します。
179. さらに初回起動の設定を保存します。
180. 設計書は意図の証拠であり、
181. 実際に拒否できた証拠とは異なります。
182. 架空データで他人の申請を拒否する試験と、
183. 自分の申請を許可する試験を対にします。
184. 職員の担当内外と提出前後も変えます。
185. 詳細、一覧、添付、一括出力を検査します。
186. 異動後と委託期限後の拒否も確かめます。
187. 判定に必要な情報が取れない場合と、
188. 正規の復旧手順を試験します。
189. 期待結果、使用した版、条件、結果を残し、
190. 観測できるログと対応させます。
191. ログがないだけでは事故なしといえません。
192. ログがあっても拒否処理の代わりにはなりません。
193. 提供者は安全な実装と標準設定を作り、
194. 運用者は業務規則と変更を管理します。
195. 委託契約では作業と証拠の担当を明示します。
196. 任せたという事実だけで責任は整理できません。
197. 本章のローカル例は規則の一部を試します。
198. 実サービス全体の安全性を証明しません。
199. 不足する証拠は未検証として残します。
200. 新しい機能や役割が増えたら、
201. 規則、初期状態、試験を見直します。

## 注意

`DRAFT v0.1 / HOLD` の未公開候補。実在する自治体への助言、法令適合判断、製品の認証、独立C受入ではない。単体モデルは一覧・添付・一括出力・初回登録・多要素認証・分散キャッシュを実装していない。必要な統合試験は別途残る。重要命題の根拠、適用条件、形式間対応は [根拠表](../SOURCE_EVIDENCE.md) と [3形式対応表](../FORMAT_MAP.md) に分離して記録する。

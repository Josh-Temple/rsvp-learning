# パスワード・MFA・フィッシング耐性

Status: COMPLETE v0.1
Created: 2026-10-08

## 学習目標

認証方式ごとの限界を説明し、利用者負担、攻撃耐性、回復性を含めて適切な認証構成を選べるようにします。

## 本文

1. 認証は利用者の証明を確認します。
2. 認可は操作の許可を決めます。
3. この二つは同じではありません。
4. パスワードは知識要素です。
5. 再利用は被害を広げます。
6. サービスごとに一意にします。
7. パスワード管理ツールが役立ちます。
8. 保存先と復旧手段も保護します。
9. 既知の漏えい候補を拒否します。
10. 複雑さだけでは安全を測れません。
11. MFAは異なる要素を使います。
12. 知識と所持は異なる要素です。
13. 二つのパスワードは一要素です。
14. OTPは一度だけ使う値です。
15. OTPも偽サイトへ渡り得ます。
16. SMSにも固有の脅威があります。
17. プッシュ通知も誤承認され得ます。
18. 番号照合でも危険は残ります。
19. 耐性は利用者の注意に依存しません。
20. 偽の検証者に秘密や有効な出力を渡しません。
21. WebAuthnは公開鍵方式を使います。
22. 認証先の名前と暗号的に結び付けます。
23. 偽サイトで認証結果を流用させません。
24. 適切な設定が前提になります。
25. Passkeyには同期型もあります。
26. 同期型と端末固定型は異なります。
27. 鍵の保存と復旧も検討します。
28. 同期できれば無条件に安全ではありません。
29. 架空の職員用システムを考えます。
30. 管理者は重要な権限を持ちます。
31. 現在はSMSの追加認証です。
32. 模擬の偽ログイン画面を想定します。
33. 入力されたコードは転送され得ます。
34. 追加認証の実施だけでは不十分です。
35. 認証先に結び付く方式を検討します。
36. 認証器の配布方法も決めます。
37. 端末を紛失した場合を想定します。
38. 回復窓口が弱ければ迂回されます。
39. 本人確認と回復手続を区別します。
40. 認証器の追加権限を限定します。
41. 追加と削除の履歴を残します。
42. 不審な登録の通知も用意します。
43. 回復の成否を模擬試験します。
44. 設定済みと実際の成功は異なります。
45. 端末紛失時の復旧時間も調べます。
46. 代替手段の強度を比較します。
47. 利用できない職員への支援も必要です。
48. アクセシビリティを検討します。
49. 高権限では強い方式を優先します。
50. 要求水準は用途ごとに異なります。
51. NISTのAALは適用条件を伴います。
52. 米国政府向け要件を一般化しません。
53. 同期型の扱いも水準で異なります。
54. 適用する規格の版を確認します。
55. 認証後のセッションも管理します。
56. 権限変更時は再評価します。
57. 成功率だけで耐性は測れません。
58. 偽サイトでの耐性を安全に検証します。
59. 認証器紛失時の回復も演習します。

## 注意

NIST SP 800-63B-4は米国デジタルIDの指針です。AAL要件をあらゆる日本の民間・自治体システムの法的義務とみなさず、認証先との結び付き、同期可能な認証器の条件、本人確認と回復・セッション管理を別々に評価します。

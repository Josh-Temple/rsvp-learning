# パスワード・MFA・フィッシング耐性

Status: COMPLETE v0.1
Created: 2026-10-08

## 学習目標

認証方式ごとの限界を説明し、利用者負担、攻撃耐性、回復性を含めて適切な認証構成を選べるようにします。

## 本文

1. パスワードは知識要素です。
2. 秘密を知っていることを使います。
3. 再利用は被害を広げます。
4. サービスごとに分けます。
5. 長さも重要です。
6. 複雑さだけに頼りません。
7. 既知の漏えいパスワードも避けます。
8. Password managerが役立ちます。
9. 一意なパスワードを管理できます。
10. 保存先自体も守ります。
11. MFAは複数要素を使います。
12. 知識要素があります。
13. 所持要素があります。
14. 生体要素があります。
15. 異なる要素を組み合わせます。
16. 二回入力するだけではMFAではありません。
17. 方式ごとに耐性が違います。
18. SMSには固有のリスクがあります。
19. OTPもフィッシングされ得ます。
20. Push通知も狙われます。
21. MFA疲労があります。
22. 誤承認を誘う攻撃です。
23. 番号照合は一部リスクを減らします。
24. フィッシング耐性を考えます。
25. FIDO系の方式があります。
26. WebAuthnが使われます。
27. 公開鍵を使う方式があります。
28. 共有秘密を送らない利点があります。
29. 認証先との結び付きも重要です。
30. 偽サイトへの入力を減らせます。
31. Passkeyもこの系統です。
32. 同期型の利用形態もあります。
33. 利用環境のリスクを評価します。
34. 回復手段は弱点になり得ます。
35. 本人確認より弱い回復を避けます。
36. サポート窓口も攻撃対象です。
37. 認証器紛失に備えます。
38. 複数の安全な回復手段を考えます。
39. 管理者は高い保護が必要です。
40. 重要システムも優先します。
41. 段階的な移行も考えます。
42. 利用不能もリスクです。
43. アクセシビリティも考慮します。
44. ロックアウト運用も設計します。
45. 異常試行を監視します。
46. 新規認証器登録も監視します。
47. 認証器削除も重要イベントです。
48. 回復操作も記録します。
49. 認証方式だけで完結しません。
50. セッション管理と組み合わせます。

## 注意

具体的な長さや保証要件を固定値として一般化しません。利用する標準、サービス、法令、組織ポリシーの現行要件を確認します。

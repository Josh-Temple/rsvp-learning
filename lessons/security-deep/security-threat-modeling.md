# 脅威モデリング

Status: COMPLETE v0.1
Created: 2026-10-08

## 学習目標

図やSTRIDEを作ること自体を目的にせず、設計上の脅威を早期に発見し、対策と検証へつなげる一連の活動として説明できるようにします。

## 本文

1. 脅威モデリングは設計判断に使います。
2. 攻撃後だけに考えません。
3. 早い段階から行えます。
4. 最初に対象範囲を決めます。
5. 何を作るかを理解します。
6. 構成要素を整理します。
7. データの流れを整理します。
8. 外部主体も整理します。
9. 信頼境界を示します。
10. 入口と出口を確認します。
11. 管理経路も確認します。
12. 前提条件も記録します。
13. 次に何が起こるか考えます。
14. 攻撃者の視点も使います。
15. 事故の可能性も含めます。
16. STRIDEは分類法の一つです。
17. なりすましを考えます。
18. 改ざんを考えます。
19. 否認を考えます。
20. 情報漏えいを考えます。
21. サービス妨害を考えます。
22. 権限昇格を考えます。
23. 分類は発想を助ける道具です。
24. 項目を埋めることが目的ではありません。
25. Misuse Caseも使えます。
26. Attack Treeも方法の一つです。
27. 複数の方法を選べます。
28. 脅威をシナリオへ落とします。
29. 対象資産を確認します。
30. 必要条件を確認します。
31. 攻撃経路を確認します。
32. 成功時の影響を考えます。
33. 既存対策も確認します。
34. 優先順位を付けます。
35. すべてを同じ重さで扱いません。
36. 次に対策を考えます。
37. 設計変更で消せる場合があります。
38. 権限を減らす場合があります。
39. 境界を追加する場合があります。
40. 検知を追加する場合もあります。
41. 復旧策も検討します。
42. 残るリスクも記録します。
43. 最後に十分かを確認します。
44. 図が最新か確認します。
45. 脅威漏れをレビューします。
46. 対策が実装されたか確認します。
47. 新しい弱点がないか見ます。
48. 変更時にモデルを更新します。
49. 新しいAPIでも見直します。
50. 委託先変更でも見直します。
51. 脅威モデルは一度きりではありません。
52. ペネトレーションテストとは違います。
53. コードレビューとも違います。
54. 相互に補完できます。
55. 成果物は図だけではありません。
56. 脅威一覧も成果です。
57. 対策と根拠も成果です。
58. 未解決事項も残します。
59. 設計の意思決定へつなげます。

## 注意

脅威モデリングには複数の方法があります。STRIDEは代表例ですが、すべての対象に唯一の正解として適用するものではありません。

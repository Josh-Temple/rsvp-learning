# RBAC・ABAC・最小権限・特権管理

Status: COMPLETE v0.1
Created: 2026-10-08

## 学習目標

権限モデルを機能一覧ではなく業務責任とリスクから設計し、付与、利用、レビュー、剥奪まで説明できるようにします。

## 本文

1. 認可は何を許すかを決めます。
2. 最小権限が基本です。
3. 必要な操作だけを許します。
4. 必要な期間だけ許します。
5. 必要な対象だけ許します。
6. RBACはRoleを使います。
7. 職務ごとにRoleを作ります。
8. 利用者へRoleを割り当てます。
9. 管理しやすい利点があります。
10. Roleが増え過ぎる問題もあります。
11. 例外が積み重なる場合があります。
12. ABACはAttributeを使います。
13. 利用者属性を使えます。
14. 資源属性も使えます。
15. 環境条件も使えます。
16. 柔軟な判断ができます。
17. 属性品質が重要です。
18. 古い属性は誤認可を生みます。
19. Policy管理も必要です。
20. RBACとABACを組み合わせる場合もあります。
21. 職務分掌も重要です。
22. 一人で完結させない操作があります。
23. 承認と実行を分ける場合があります。
24. 利益相反も考えます。
25. 特権は影響が大きい権限です。
26. 管理者権限を常用しません。
27. 通常IDと管理IDを分けます。
28. PAMを使う場合があります。
29. 特権利用を記録します。
30. Credentialを保護します。
31. JITアクセスもあります。
32. 必要時だけ権限を上げます。
33. 期限を設けます。
34. 承認を要求する場合があります。
35. 操作記録も残します。
36. Break glassも設計します。
37. 非常時だけ使います。
38. 利用後に必ずレビューします。
39. Service accountも管理します。
40. 人の退職では消えない点に注意します。
41. 所有者を明確にします。
42. 用途を限定します。
43. 不要な権限を削ります。
44. Access reviewを行います。
45. 権限棚卸しを繰り返します。
46. 付与根拠を確認します。
47. 利用実績も確認します。
48. 異動時に再評価します。
49. 例外権限に期限を付けます。
50. 権限Lifecycleを閉じます。

## 注意

RBACやABACは万能な優劣関係ではありません。対象システムの複雑さ、属性品質、運用能力に応じて選びます。

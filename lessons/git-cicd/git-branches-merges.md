# BranchとMerge

Status: COMPLETE v0.1
Created: 2026-09-27

## 学習目標

作業を分離するBranchと、変更を統合するMergeの基本を学びます。

## 本文

1. 二人が同じ案内文の一行を別々のブランチで直したとします。
2. 先に統合された変更の後で、もう一方を統合すると競合が起こりえます。
3. Branchは、変更の流れを分けるために使います
4. mainとは別に作業用Branchを作ることができます
5. 他の変更から独立して作業しやすくなります
6. 作業が終わったら、変更を統合します
7. これがMergeです
8. 同じ箇所を別々に変更すると、Conflictが起きることがあります
9. Conflictでは、どの変更を残すか判断します
10. Branchを長期間分離すると、差分が大きくなりやすくなります
11. 小さく統合する方が、競合を減らせる場合があります
12. Merge commitを残す方法があります
13. 競合が出たときに必要なのは、二つの文を機械的に連結することではありません。
14. Squashで複数Commitを一つにまとめる方法もあります
15. Rebaseで履歴を並べ直す方法もあります
16. 運用方法は、チームのルールに合わせます
17. 重要なのは、変更経路を追えることです
18. 双方の意図を読み、採用する文章を決めてから競合を解消します。
19. 自動的に結合できても内容が矛盾することがあります。
20. 統合後に差分とテストを確認します。
21. どちらの修正理由を残すか確認し、統合した結果が意図した案内になったか見ます。
22. 二つのブランチが別の行で期限を変えます。
23. 自動統合後も画面と案内の期限が食い違います。
24. 関連する表示をまとめて確認します。
25. 競合がなければ正しい統合ですか。
26. 意味の矛盾は人が見つけます。

## 注意

この章は基礎理解用です。
実務で判断するときは、対象システムの仕様、組織ルール、データの前提を別途確認します。

# 統合ケース3: データ・API・アーキテクチャ

Status: COMPLETE v0.1
Created: 2026-09-29

## 学習目標

業務上の情報をデータ構造へ落とし、正本、履歴、API契約、同期・非同期、再試行、冪等性をつないで、障害時にも状態を説明できる設計を考えられるようにします。

## 本文

1. 申請を一つの塊にしません。
2. 申請者を分けて考えます。
3. 申請本体も分けます。
4. 添付情報もあります。
5. 審査状態も持ちます。
6. 担当情報も必要です。
7. 関係を明確にします。
8. 重複Dataを減らします。
9. どれが正本か決めます。
10. 派生情報と分けます。
11. 状態変更を履歴に残します。
12. 現在値だけでは足りません。
13. 誰が変えたか残します。
14. いつ変えたかも残します。
15. 過去時点を再現できるようにします。
16. 監査にもつながります。
17. APIは画面の裏の契約です。
18. Requestを定めます。
19. Responseも定めます。
20. Errorも定めます。
21. Versionを意識します。
22. 利用側を突然壊しません。
23. 認証と認可も必要です。
24. 対象単位で権限を見ます。
25. 即時処理が必要か考えます。
26. 受付番号は即時に返します。
27. 重い集計は後でもよいです。
28. 通知も非同期にできます。
29. 完了前の状態を持ちます。
30. Queue遅延も想定します。
31. 順序逆転もあり得ます。
32. 完了条件を明確にします。
33. 通信失敗では結果が不明です。
34. 安全に再試行できるようにします。
35. Idempotencyを使えます。
36. 処理IDを持たせます。
37. 重複登録を防ぎます。
38. 同じ依頼を識別します。
39. 失敗を成功扱いしません。
40. 結果確認経路を用意します。
41. DB成功と通知失敗を分けます。
42. 途中成功を想定します。
43. 補償処理も考えます。
44. 一貫性が遅れる場合があります。
45. 画面へ状態を示します。
46. 観測用Logを残します。
47. 障害を追跡できるようにします。
48. 状態の確定点を説明します。

## 注意

この章は概念設計のケースです。具体的なDB製品、API方式、Message Queue製品の選定は扱いません。

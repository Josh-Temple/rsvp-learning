# 統合ケース4: Security・Cloud・復旧

Status: COMPLETE v0.1
Created: 2026-09-29

## 学習目標

機能が動くだけでなく、安全性と復旧性を満たすために、権限、通信、責任分界、監視、Backup、復旧目標を業務影響とつなげて設計できるようにします。

## 本文

1. まず守る情報を確認します。
2. 申請Dataがあります。
3. 本人情報も含みます。
4. 完全性も重要です。
5. 可用性も必要です。
6. 脅威と弱点を考えます。
7. 影響の大きさも見ます。
8. Riskに応じて対策します。
9. 本人確認と権限は別です。
10. Login成功だけでは不足です。
11. 申請者は自分の情報だけ見ます。
12. 審査者には別権限があります。
13. 管理者権限を絞ります。
14. 最小権限を使います。
15. 異動時に権限を見直します。
16. 共用IDを避けます。
17. Cloud事業者にも責任があります。
18. 利用組織の責任も残ります。
19. 設定責任を曖昧にしません。
20. App事業者も関係します。
21. 運用事業者も関係します。
22. 障害切分けを決めます。
23. 契約終了も想定します。
24. Data返却も確認します。
25. 通信を暗号化します。
26. 秘密情報をCodeへ埋めません。
27. 秘密の保管先を決めます。
28. Network経路を把握します。
29. 公開範囲を絞ります。
30. 不要Portを開けません。
31. 証明書期限も監視します。
32. 設定変更を記録します。
33. Backupを取ります。
34. 復元試験も行います。
35. RTOを業務から決めます。
36. RPOも業務から決めます。
37. 障害種類を分けます。
38. 単一障害だけを考えません。
39. 依存Serviceも確認します。
40. 代替手順も準備します。
41. 異常を監視します。
42. 失敗率を見ます。
43. 権限異常も見ます。
44. 不審Accessも確認します。
45. Incident時は封じ込めます。
46. 影響範囲を確認します。
47. 復旧後に原因を見直します。
48. 再発防止へつなげます。

## 注意

具体的なCloud設定や法令要件はサービスと組織により異なります。この章では責任分界と復旧設計の考え方を扱います。

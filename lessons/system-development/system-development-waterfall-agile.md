# WaterfallとAgile

Status: COMPLETE v0.1
Created: 2026-09-27

## 学習目標

代表的な開発アプローチであるWaterfallとAgileの違いと使い分けの考え方を学びます。

## 本文

1. 申請制度の確定した要件をまとめて設計し、段階ごとに確認する進め方を考えます。
2. 別の進め方では、受付だけ先に試し、利用者の反応を見て改善します。
3. WaterfallとAgileは、開発の進め方を考える代表的な枠組みです
4. Waterfallでは、工程を順に進める形が基本です
5. 初期に要件や計画を明確にすることを重視します
6. ただし、工程が進んだ後の変更は影響範囲が広くなる場合があります。
7. 案件の規模だけで、進め方を選ぶわけではありません。
8. Agileでは、小さな単位で作り、確認し、改善を繰り返します
9. 早い段階で利用者からフィードバックを得やすくなります
10. 不確実性が高い領域に向く場合があります
11. ただし、Agileでも計画や品質管理は必要です
12. Waterfallでも、途中の検証や改善はできます
13. 要件が固まっていても途中変更は起こり、反復を選んでも規制上の条件は残ります。
14. 実務では、両者を組み合わせることもあります
15. 重要なのは、名称ではなく要求の不確実性や変更頻度に合う進め方です
16. 契約、組織、規制、技術条件も選択に影響します
17. 手法を目的化せず、価値を届ける方法として考えます
18. 途中で制度が変われば、どちらも影響範囲と承認を確認します。
19. 短い反復でも法令上の要件を省けません。
20. 変更の頻度と利用者の関与に合わせて進め方を選びます。
21. 利用者がいつ確かめられるか、変更をどう取り込むかで進め方を比較します。
22. 短い反復で受付画面を先に公開するとします。
23. 審査規程が未確定なら、受付可否を決められません。
24. 反復の範囲と確定が必要な条件を分けます。
25. 反復型なら承認を後回しにできますか。
26. 規程上の確認は進め方と独立に必要です。

## 次に確認したいこと

この章は基礎理解用です。
具体的な製品仕様、組織固有の工程名、法令上の要件は、この章だけで確定しません。
必要に応じて公式資料・一次資料で確認します。

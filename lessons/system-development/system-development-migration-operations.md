# 移行と運用設計

Status: COMPLETE v0.1
Created: 2026-09-27

## 学習目標

新システムへの切替と、リリース後に安定運用するための準備を学びます。

## 本文

1. 紙台帳の申請を新システムへ移すとします。
2. 氏名だけでは同姓同名を区別できず、件数一致だけでは正しい移行とは言えません。
3. システムは、完成しただけでは利用できません
4. 移行では、旧環境から新環境へ切り替えます
5. データ移行では、形式と意味の両方を確認します
6. 欠損や重複がないか検証します
7. 利用者や権限の移行も必要になることがあります
8. 本番切替の手順を事前に決めます
9. 失敗した場合の戻し方も準備します
10. これが、rollbackの考え方です
11. 運用設計では、誰が何を監視するかを決めます
12. 障害時の連絡先と判断権限を明確にします
13. 移行前後で件数が一致しても、別人の申請へ情報を結びつければ失敗です。
14. バックアップと復旧手順を確認します
15. 問い合わせ対応や変更手順も設計します
16. 運用担当へ必要な情報を引き継ぎます
17. 良い移行は、技術だけでなく業務継続を守ります
18. 移行前後の識別子、重要項目、件数を照合します。
19. 失敗した場合に旧台帳へ戻す期限と手順を決めます。
20. 切替後の問い合わせ、バックアップ、障害対応の担当も用意します。
21. 識別子と重要項目を照合し、戻せる期限を越える前に切替可否を決めます。
22. 移行後に同じ人が二件に分かれたとします。
23. 旧台帳では氏名の表記が揺れていました。
24. 統合規則を決め、元の記録を残して照合します。
25. 件数が一致すれば重複もないでしょうか。
26. 重複と誤結合は別に調べます。

27. 移行前に照合基準を決めます。
28. 件数以外の整合性も確認します。
29. 切替条件を事前に定めます。
30. 戻す条件も決めておきます。
31. 運用手順を実地で試します。
32. 権限移行も忘れません。
33. 監視と問い合わせ先を準備します。
34. 安定後に旧環境を閉じます。

## 次に確認したいこと

この章は基礎理解用です。
具体的な製品仕様、組織固有の工程名、法令上の要件は、この章だけで確定しません。
必要に応じて公式資料・一次資料で確認します。

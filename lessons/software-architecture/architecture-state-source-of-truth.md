# 状態管理とSingle Source of Truth

Status: COMPLETE v0.1
Created: 2026-09-27

## 学習目標

複数の場所に状態を持つ難しさと、正本を明確にする設計の基本を学びます。

## 本文

1. 申請の状態をデータベースでは承認済み、画面のキャッシュでは審査中と表示したとします。
2. どちらを正本とするか決めていなければ、訂正時に混乱します。
3. 状態は、システムが現在どの状況にあるかを表します
4. 例えば、申請中、承認済み、取消済みなどがあります
5. 同じ状態を複数の場所で管理すると、ずれが起こることがあります
6. どの情報について、どこを正本とするかを決めます
7. Single Source of Truthは、特定の情報について、正しい値を参照する基準を定める考え方です
8. 他の画面や集計表は、正本から派生させます
9. 派生データは、遅れて更新される場合があります
10. その場合、どの程度の遅延を許すか考えます
11. 状態変更には、権限と条件を設けることがあります
12. 不正な順序で状態が変わらないようにします
13. 表示のキャッシュが古くても、正本の状態まで書き換える理由にはなりません。
14. 履歴を残すと、後から変化を追えます
15. 更新が途中で失敗した場合の扱いも決めます
16. 状態と履歴を混同しないことが重要です
17. 正本と派生情報を区別すると、復旧しやすくなります
18. 更新の権限と順序を定め、表示側は正本から状態を反映します。
19. 反映が遅れる場合は許される時間と利用者への表示を考えます。
20. 履歴を残して変更理由を追います。
21. 正本を決め、反映の遅れを示し、変更履歴を残すことで食い違いを調べられます。
22. キャッシュが承認済みを先に示したとします。
23. 正本が審査中なら、表示が先走っています。
24. 表示の更新経路と反映時間を調べます。
25. 二つの値を同格に扱えますか。
26. 決めた正本で訂正します。

27. 正本は情報の種類ごとに決めます。
28. すべてを一か所へ集める意味ではありません。
29. 派生値には生成元を残します。
30. 更新責任者を明確にします。
31. 反映遅延を監視します。
32. 履歴と現在値を分けます。
33. 訂正手順も決めておきます。
34. 復旧時は正本から再構築します。

## 注意

この章は基礎理解用です。
実務で判断するときは、対象システムの仕様、組織ルール、データの前提を別途確認します。

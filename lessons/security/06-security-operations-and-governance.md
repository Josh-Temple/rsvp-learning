# 組織としてのセキュリティ運用の全体像

Status: Draft v0.3  
確認日: 2026-09-27

この原稿は、組織的なセキュリティ運用の全体像をつかむための章です。

リスク管理、ISMS、監視、インシデント対応、事業継続の詳細は、それぞれの専用原稿で扱います。

## 1. セキュリティは組織の活動である

情報セキュリティは、セキュリティ担当者だけの仕事ではありません。

経営層。

システム担当者。

利用者。

委託先。

それぞれに役割があります。

組織として、何を守るかを決めます。

どのリスクを受け入れるかを決めます。

誰が判断するかを明確にします。

## 2. 方針と責任を決める

技術対策を導入する前に、組織としての方針と責任を明確にします。

誰が情報を所有するか。

誰が権限を承認するか。

重大な事故を誰へ報告するか。

例外を誰が認めるか。

こうした判断の仕組みが必要です。

NIST Cybersecurity Framework 2.0では、このような統治をGovernとして扱います。

## 3. リスクを基準に対策を選ぶ

すべてのシステムへ同じ対策を適用するわけではありません。

扱う情報。

業務への影響。

脅威。

脆弱性。

法令や契約。

これらを踏まえて優先順位を決めます。

対策の数ではなく、重要なリスクを管理できているかを見ます。

## 4. 日常運用で状態を保つ

安全な状態は、設計しただけでは維持できません。

アカウントを見直します。

ソフトウェアを更新します。

設定変更を管理します。

ログを確認します。

バックアップを確認します。

教育を行います。

委託先の変更にも対応します。

日常運用がセキュリティを支えます。

## 5. 異常を見つけて対応する

問題を完全に防げない以上、異常を見つける仕組みが必要です。

ログや監視から兆候を確認します。

インシデントが起きた場合は、被害を抑え、調査し、復旧します。

技術担当だけでなく、経営、法務、広報、委託先などとの連携が必要になる場合があります。

## 6. 復旧できるようにする

障害や攻撃でシステムが停止する可能性があります。

バックアップ。

冗長化。

復旧手順。

代替業務。

連絡体制。

必要な準備を事前に行います。

復旧方法は、実際に試さなければ機能するか分かりません。

## 7. 委託先とサプライチェーン

組織の情報やシステムは、自組織だけで完結しません。

クラウド事業者。

ソフトウェア提供者。

保守会社。

業務委託先。

外部組織を通じてリスクが入る可能性があります。

どの情報と権限を渡しているかを把握します。

事故時の連絡や責任分担も決めます。

## 8. 人の注意だけに依存しない

利用者への教育は重要です。

しかし、事故が起きるたびに注意だけを求める方法には限界があります。

誤操作しにくい設計。

不要な権限を与えない仕組み。

多要素認証。

異常検知。

安全側へ倒れる仕組み。

人が間違える可能性を前提に、技術と運用を組み合わせます。

## 9. 継続的に改善する

システム。

脅威。

業務。

法制度。

委託先。

環境は変化します。

監査やインシデントから得た知見を使い、対策を見直します。

新しい対策を増やすだけでなく、不要になった手順や重複した管理を減らすことも改善です。

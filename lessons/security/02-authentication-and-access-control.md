# 2. 認証とアクセス制御

Status: Draft v0.3  
確認日: 2026-09-27

## 1. 識別、認証、認可

システムを安全に使うには、誰が利用しているかを確認し、許された操作だけを実行できるようにする必要があります。

利用者が自分のIDを示すことは、識別と呼ばれます。

その利用者が本当に本人であることを確認する処理が認証です。

認証された利用者に、どの操作を許可するかを決めることが認可です。

認証に成功したことと、すべての情報へアクセスしてよいことは同じではありません。

## 2. パスワード

パスワードは、利用者が知っている情報を使う認証方法です。

同じパスワードを複数のサービスで使い回すと、一つのサービスから認証情報が漏れたときに、別のサービスまで不正利用される危険が高まります。

推測しやすい短いパスワードも危険です。

サービスごとに異なる十分な長さのパスワードを使い、パスワードマネージャーを利用して管理する方法があります。

NIST SP 800-63B-4では、単一要素として使うパスワードについて、最低15文字を求めています。

多要素認証の一部として使う場合は、最低8文字としています。

これは米国政府向けデジタルID指針における検証側の要件であり、あらゆるサービスにそのまま適用される共通ルールではありません。

同じ指針では、根拠のない定期変更を要求せず、認証情報が侵害された証拠がある場合に変更を求めます。

長さだけでなく、既知の弱いパスワードや漏えい済みパスワードを避けることも重要です。

## 3. 多要素認証

認証に使う要素は、大きく知識、所持、生体などに分けられます。

パスワードは知識要素です。

セキュリティキーや端末などは所持要素として利用できます。

指紋や顔などは生体要素として利用できます。

異なる種類の要素を組み合わせて認証する方法が、多要素認証です。

多要素認証を使えば、パスワードが盗まれただけでは認証を突破できない可能性が高くなります。

ただし、多要素認証ならどの方式でも同じ強さというわけではありません。

一部の方式では、偽サイトへ入力した認証情報や確認コードを攻撃者に中継される可能性があります。

CISAは、FIDOやWebAuthnを利用する方式を、広く利用可能なフィッシング耐性のある認証として推奨しています。

高い保護が必要なアカウントでは、方式の違いまで考えることが重要です。

## 4. アクセス制御

認証後は、その利用者が必要な情報や機能だけへアクセスできるようにします。

これがアクセス制御です。

必要以上の権限を与えると、アカウントが侵害された場合の被害が大きくなります。

業務に必要な最小限の権限だけを付与する考え方を、最小権限の原則と呼びます。

管理者権限は特に強い権限です。

通常業務で常に管理者権限を使うより、必要な場面だけ高い権限を使う設計が安全です。

## 5. 権限は継続的に見直す

アクセス権は、一度設定して終わりではありません。

異動、退職、担当変更などによって必要な権限は変化します。

使われなくなったアカウントや不要になった権限を残すと、攻撃者に悪用される入口になる可能性があります。

アカウントと権限を定期的に確認し、不要なものを削除する運用が必要です。

## 6. 生体認証は確率的に判定する

指紋や顔などの生体情報では、入力した特徴と登録済みの特徴が十分に近いかを判定します。

そのため、正しい本人を一致しないと判定する場合があります。

これをFalse Non-Match、偽非一致と呼びます。

反対に、別人を本人と一致したと判定する場合があります。

これをFalse Match、偽一致と呼びます。

しきい値を厳しくすると偽一致を減らせる一方、本人を拒否する可能性が高まることがあります。

生体認証は「完全に一致するか」を見る単純な仕組みではありません。

また、生体特徴はパスワードのように簡単に変更できません。

NISTのデジタルID指針でも、生体情報の利用には制約があり、ほかの認証要素と組み合わせて扱います。

## 7. SSOと認証連携

Single Sign-On、SSOでは、一度の認証を基に複数のサービスへアクセスできるようにします。

サービスごとに別のパスワードを持つ負担を減らせます。

現在のSSOでは、Identity Provider、IdPが利用者を認証し、利用先のサービスへ認証結果を伝える連携方式がよく使われます。

利用先はRelying Party、RPなどと呼ばれます。

NISTは、このような仕組みをFederation、認証連携として整理しています。

認証を集中させることで管理を統一しやすくなります。

一方、IdPが侵害されると複数サービスへ影響する可能性があります。

SSOは「パスワードを一回入力すれば安全」という機能ではなく、信頼関係、認証強度、セッション、連携情報の検証まで含めて設計します。

## 8. 状況に応じて認証を強化する

通常と異なる端末。

通常と異なる場所。

不自然な時刻。

短時間の大量アクセス。

こうした情報を追加の判断材料として使う認証があります。

リスクが高いと判断した場合だけ、追加認証を求める方法もあります。

ただし、行動や位置情報からの推定は誤る可能性があります。

リスク判定だけを本人確認そのものと考えず、認証要素やアクセス制御と組み合わせます。

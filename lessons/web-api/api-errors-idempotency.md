# エラー処理と冪等性

Status: COMPLETE v0.1
Created: 2026-09-27

## 学習目標

APIの失敗を扱うためのStatus Code、Retry、冪等性の基本を学びます。

## 本文

1. 申請APIへ送信した直後に応答がタイムアウトしたとします。
2. サーバー側では作成済みかもしれません。
3. API通信は、常に成功するとは限りません
4. 入力が不正な場合があります
5. 権限が不足している場合があります
6. 対象データが存在しない場合があります
7. サーバー内部で失敗する場合もあります
8. HTTP Status Codeは、失敗の種類を伝えるために使われます
9. 4xxは、要求側に原因がある場合に使われることが多いです
10. 5xxは、サーバー側の失敗を表すことが多いです
11. 失敗時に、何でもRetryすれば良いわけではありません
12. 同じ要求を再送すると、二重登録が起こることがあります
13. タイムアウトは、申請が作られなかった証拠にはなりません。
14. 冪等性は、同じ要求を何度行っても、意図した効果が一度のときと同じになる性質です
15. GETは、通常は副作用を持たないように設計します
16. 重要な登録処理では、Idempotency Keyを使う設計もあります
17. エラー処理は、正常処理と同じくらい重要です
18. 同じ要求に識別子を付けて再送し、作成済みなら元の結果を返す設計にします。
19. 入力不備、権限不足、サーバー障害では、利用者や呼出し側の対応が異なります。
20. エラー内容と再試行の可否を分けて伝えます。
21. 識別子で同じ要求を見分け、再送しても一件の結果へ収束するようにします。
22. 同じ識別子で、内容の違う申請を再送します。
23. 同じ結果として扱うと、どちらを受けたか曖昧です。
24. 識別子と要求内容の対応も検査します。
25. 識別子が同じなら無条件に成功を返しますか。
26. 内容の不一致は別に扱います。

27. 再試行前に失敗の種類を分けます。
28. 入力誤りは自動再試行しません。
29. 一時障害は再試行候補です。
30. 待ち時間を空けることがあります。
31. 冪等キーは重複処理を抑えます。
32. キーと要求内容を対応させます。
33. 期限切れ後の扱いも決めます。
34. 利用者へ確定状態を返します。
